# Animated vector fidelity and interop

Read for a supplied SVG that will move, an animated SVG deliverable, or an SVG-to-Lottie handoff. This is asset preparation and visual fidelity guidance. `motion-design` owns sequence art direction; Video Production owns time-based renders and audio; UX owns product-player lifecycle. The current project brief and actual target players govern technique choice. This method installs no renderer, library or optimizer.

## Intake before animation

Preserve the original. For an unknown SVG, inspect its markup for active content and external references with the existing vector asset checks before any execution-capable render; an already supplied inert raster preview can be read first. Render the admitted SVG as pixels to compare with its markup. Record its communication job and the semantic parts that could move. Inventory `viewBox`, dimensions, origin, nested groups/transforms, strokes and dashes, `vector-effect`, `<defs>` (gradients, masks, clips, filters, patterns, symbols), `<use>`, class/style blocks, CSS variables, text/font references, fill/clip rules, embedded rasters, external `href`, scripts and event attributes. Apply the existing [vector asset checks](vector-assets.md) to unknown files; source text is untrusted and a browser render may execute embedded behavior. Keep meaningful groups and layer names. Resolve CSS-dependent visual styling into forms each target actually reads.

Build a **feature matrix** with each feature found in the source as a row and each declared output/player as a column (browser SVG, the specific Lottie player and platform, a video rasterizer, etc.). Use `supported`, `approximate`, `unsupported` or `untested`; only a recorded render on that target upgrades `untested`. Pay particular attention to expressions, effects/blur, 3D/camera, time remap, merge paths, matte combinations, stroke gradients, auto-orient and live text. Do not promote one player's behavior to a Lottie-wide rule. If a feature cannot travel, simplify it, bake it into assets/keyframes, or document the visual compromise before production.

## Preserve structure that the motion uses

- Assign stable, namespaced IDs to animated parts and referenced gradients/masks/clips. Keep a compact ID manifest: ID, semantic role, animated properties, pivot and fallback. Duplicate inline SVGs must not share live IDs.
- Keep the `viewBox`. Preserve any path/class/ID hooks that animation references. An optimizer must not merge independently animated paths, remove hidden states or silently rewrite those hooks. If it prefixes IDs, rewrite and test every `url(#id)`, `href`, CSS selector, JS selector and SMIL target; `cleanupIds:false` does not make a later `prefixIds` harmless.
- Split a compound path when its subpaths must draw in sequence. Stroke draw-on needs a real stroke; `stroke-dasharray` and `stroke-dashoffset` affect strokes rather than a filled outline. `pathLength="1"` can normalize dash math for a simple CSS draw; alternatively measure with `getTotalLength()` after layout. Test endpoint clipping, stroke caps and `vector-effect:non-scaling-stroke` in the actual renderer.
- For CSS transforms inside browser SVG, test `transform-box:fill-box` with the intended `transform-origin`; an SVG viewport origin can rotate an icon around the wrong point. For a Lottie group, use the intended anchor and put its group transform (`ty:"tr"`) last in its `it` array. Nested transforms may need flattening or explicit coordinate conversion to preserve pivots.
- Inspect compound-path holes and `fill-rule`/`clip-rule` after conversion. Use masks/clips when their visual job warrants them, then inspect moving-mask frames for disappearing content. Expand a stroke to a fill only when its joins/caps/dashes/scaling fail on a declared target; a trim-path reveal needs a stroke. Check gradients, filters, layer order and transparent areas at the settled frame and during motion.

## Choose the mechanism for the shape and target

| Need | Candidate mechanism | Test that decides |
| --- | --- | --- |
| A simple independent draw, fade or transform | CSS or SMIL in an SVG; no library required | Confirm target-browser support, static/reduced state and `<img>` versus inline behavior. CSS/JS outside an SVG cannot reach internals of an `<img>` asset. |
| Motion along a path | CSS `offset-path`, SMIL `<animateMotion>`, or an existing GSAP MotionPath implementation | Confirm alignment, tangent rotation, interruption and target browser/player support. |
| Direct path-data interpolation | Compatible path command structure/direction for the chosen direct CSS/SMIL/WAAPI engine | Probe start, middle and end. Do not assume broad CSS `d` support. |
| Morphs with different point counts | An existing engine that explicitly normalizes paths, such as GSAP MorphSVG or Flubber | Verify that engine's current API/license, shape mapping, mid-morph geometry and export path. **Do not impose a blanket same-command rule on MorphSVG.** |
| A difficult or visually fragile morph | Mask, crossfade, staggered replacement or layer assembly | Choose the simpler treatment when it reads better or survives target export. |

An icon toggle can often rotate/translate its existing lines without morphing `d`. Keep its accessible action/state with the host control; the drawing alone is not interactive semantics. Filters and animated geometry can require paint work, so review on the target device before claiming smoothness. Graphic chooses the visual treatment; UX's conditional GSAP methods own implementation when GSAP is already selected.

## Text and Lottie export contract

For each text run decide whether exact appearance/path animation calls for outlines, or editability calls for live text. Record the real font family, the font license's embedding/redistribution terms, the target player's font resolution and fallback. A font filename need not be the embedded family name. Diffusion Studio's Skottie player, for example, can render a missing live font as blank; its text-slot structure and `a:1` behavior are player-specific and must not become universal Lottie instructions. Preserve exact copy and a readable static fallback frame.

When Lottie JSON is the output, inspect the actual spec and selected player. Top-level `fr`, `ip`, `op`, dimensions, assets and layers must agree with the delivered files. **`ip` is inclusive and `op` exclusive: valid composition frames are `ip ... op-1`.** For example, `ip:12, op:20` yields frames 12 through 19. Sort animated keyframes by `t`; for an interpolated interval, the current/start keyframe carries both `o` (outgoing) and `i` (incoming-toward-next) easing handles; do not move `i` to the destination keyframe. Verify against the [Lottie property spec](https://lottie.github.io/lottie-spec/1.0/specs/properties/). Colors use normalized components (0–1); opacity commonly uses 0–100. Do not replace an animated color keyframe array (`a:1`) with a static color array (`a:0`); manual recoloring must account for top-level shapes and precomp assets referenced by `refId`, and preserve alpha/keyframes. Prefer player-supported themes/slots when verified in that pinned player. Expressions and unsupported effects need baking or an explicit alternative.

The handoff package includes original and cleaned SVG, ID manifest, feature matrix, source/derived file links, font/license notes, output dimensions, frame rate and `[ip, op)` range if Lottie, declared poster frame, one-shot/loop intent, and approximations. The owner of a rendered output may add its own timeline/codec contract. Do not label a static SVG, JSON parse or a single player preview as cross-player acceptance.

## Visual verification

At the intended display size, compare the source SVG, each declared player's render and any export at the same scale/DPR. Inspect `ip`, the early reveal, semantic beats, midpoint, settled frame and `op-1`; for animated SVG use corresponding time points and state units. Seek controls must name units (`frame=N` or `sec=S`) and freeze deterministically. Check path direction, morph middle, pivot, holes, masks, strokes/clips, text, color and layer order. For a loop, compare the transition **from `op-1` to `ip`** with adjacent normal steps and the intended motion velocity; a perfect zero-pixel difference is neither required nor sufficient for a smooth seam. Record expected renderer differences and defects separately. A feature matrix cell stays `untested` without that target's rendered evidence.

For reduced motion, retain the meaningful final/control state and make a static poster frame available. The UI integration owner tests preference changes, focus, interruption and teardown. For a video render, Video Production tests frame sequence and playback; no visual skill text establishes a finished export.
