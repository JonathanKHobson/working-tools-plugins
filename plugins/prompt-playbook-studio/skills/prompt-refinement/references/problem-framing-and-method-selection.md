# Frame the problem and select the method

Use when a meaningful task has unclear goals or causes, a proposed fix rests on an untested explanation, the assistant keeps returning familiar answers, or a domain method could materially improve the result. A clear routine request goes directly to execution. This is conditional depth under prompt refinement and ambition within scope, not a new planning phase. Use current conversation and project evidence; do not make the user restate known facts. Keep the analysis internal except for decisions, uncertainties or access needs that affect the work.

## Understand before selecting a solution

Preserve the user's chosen goal, deliverable, identity and authority. Separate the observation, the user's proposed explanation and the intended outcome. Check whether the difficulty is an unclear problem, missing evidence, a disputed mechanism, an execution barrier or an opportunity without a defect. A problem can have several interacting causes. Do not manufacture a hidden root cause or reinterpret an explicit preference as an error.

When the explanation matters, make it a hypothesis and identify the smallest observation that could distinguish it from the strongest plausible alternative. Prefer an available reproducer, source record, test, user evidence or applicable primary guidance over a confident expert voice. A role instruction does not supply domain knowledge or observation. If the problem is still unclear, choose a bounded discovery action whose result would change the next step. Ask only for a consequential missing fact; continue independent authorized work meanwhile.

If even the failure is unspecified, first establish the observed symptom and expected outcome. Do not select a favorite failure point from recollection and seek only confirmation. Choose a check that could reject the proposed explanation as well as support it.

A reframe can expose an ineffective proposed mechanism, but it cannot silently replace the requested output or introduce a new goal. Explain a consequential conflict and resolve it within current authority. A cheaper unrelated deliverable is not an equivalent solution. Preserve an explicit proposal-only or brainstorming-only request; an execution request should continue through delivery and verification.

## Choose the smallest sufficient support

Select support for the specific uncertainty, not to fill a checklist:

| Need | Useful support | Evidence required |
| --- | --- | --- |
| Unclear owner or missing specialist | Work Management's live skill discovery, then the selected full skill | Actual enabled entrypoint and its applicable procedure; a search hit alone is not application |
| A nontrivial thinking or activity method would improve the task | Existing Prompt Playbook procedures, or the relevant scoped Atlas search and exact-ID read | Complete selected method, fit, constraints, review/source status and adaptation limits |
| A factual premise is uncertain, current or contested | Appropriate primary sources, project records or direct observation | Source support for the claim, relevant date/context and contrary evidence where material |
| Useful independent exploration, implementation or critique | Existing authorized worker and tracked toolkit | Completed output, actual model evidence, permitted scope and lead verification |
| A known, bounded task with adequate evidence | Existing workflow and direct execution | The requested result and proportionate verification |

Use an already loaded adequate method without another lookup. When ownership is unclear, resolve `work-management:tool-workflow-routing` and call its discovery tool; do not merely recommend it. For an actual Atlas method gap, select the scoped studio route, search a few candidates and read the relevant exact IDs before application. Keep the corpus external and preserve source provenance. For a specifically requested framework comparison, use the existing Pattern Picker procedure rather than inventing a competing selector. A familiar framework's name is not proof it fits or was retrieved.

Use actual available capabilities within scope. A skill's presence does not prove its service is authenticated or working. If access is missing, state the specific gap, distinguish a technical failure from no search results, and continue with supported work. Request only the necessary unresolved access or human decision. Do not install, expand permissions, switch to paid services, publish or begin monitoring as a side effect of problem discovery.

## Widen the search where it can change the answer

Keep the first plausible answer as a baseline. Retain it if it survives task-based comparison; being first or conventional is not a defect. For consequential open choices, consider alternatives that differ in mechanism, evidence or constraints, including a simple existing approach and an approach outside the initial framing when useful. In creative ideation, vary the generating material or analogy before selecting; synonym swaps and repeated calls with the same brief are weak diversity. Do not trade truthful specifics, accessibility or task success for novelty.

Research diversity means different underlying evidence or failure conditions, not several pages repeating one source. Check shared provenance. A source outside the dominant view earns attention through relevance and evidence, not merely dissent. Multiple models can share assumptions, training and sources. Give workers useful distinct assignments or independent initial exploration; do not present model agreement as factual corroboration, a user study or proof of completeness. Preserve disagreements that could change the decision and resolve factual questions against sources or observations.

Assess factual support independently of familiarity or plausibility. Both ordinary and surprising claims can need evidence. A proposed demonstration's outcome remains hypothetical until observed; do not promise that a live model will produce a particular error or insight.

Frameworks organize inquiry; they do not validate conclusions. Avoid compulsory root-cause chains, research, worker votes or alternative quotas. Model-generated likelihoods can guide creative sampling but are not measured population rarity, calibrated confidence or proof that an idea is original. Do not promise globally unique output without an adequate comparison basis.

## Deliver and continue within scope

Choose the simplest configuration that can produce and verify the requested outcome. Explain the selected method, evidence or access need briefly when it changes the user's decision; do not narrate every internal check. A requested proposal or workflow should state the problem as currently understood, viable solution, relevant uncertainty, necessary tools/access and observable acceptance. If the next step is discovery, name what it will distinguish and when to stop. Do not propose a full implementation as though the diagnosis were established.

For authorized execution, take the next useful action and finish the result. Resolve observed blockers and nearby defects that are necessary to the same outcome. Flag an adjacent opportunity separately if it would create a competing goal, commitment or scope expansion. Proactivity does not authorize an endless improvement loop or future recurring work.

Stop when the scoped acceptance criteria are met, further information would not change the next action, or a specific missing input or authority blocks progress. Report observations, judgments and untested outcomes separately. Do not substitute a plan, a tool inventory or agreement between models for the actual result.

## Maintenance boundary

Original local integration of problem framing, evidence checks, method selection and bounded execution prompted by user-supplied AI-literacy transcripts. Those anecdotes do not establish a universal cause or measure of model homogeneity. Primary research and contrary analyses, worker dispositions and behavioral limits are recorded in the owning maintenance record. No external prompt text, private Atlas body, corpus or new runtime is bundled here.

## When a resource site could help

If a design or build prompt names a reference site or lacks a consequential example, resolve the installed `work-management` root through skill discovery and inspect `references/operations/resource-directory.json` plus `resource-access.md` for a relevant on-demand route. Select only evidence that could change the deliverable. Record the exact page or item, observed feature, access limit and intended structural adaptation in the existing brief. An index entry or visual similarity is not task evidence, a usage license, or proof of an API Anything recipe. Preserve the user's identity and approved references ahead of external inspiration.
