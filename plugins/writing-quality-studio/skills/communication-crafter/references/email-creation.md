# Email creation and personalization

Use for event follow-ups, resource emails or a batch sharing a common body. Finish the requested draft/send/schedule state. Do not load design, marketing and research specialists for an ordinary reply.

## Build one factual base, then personalize the differences

- Read one relevant prior email for voice and structure when available. Reuse that review within the task; do not repeatedly retrieve samples per recipient or save private writing samples as a reusable asset.
- Resolve a compact fact set first: purpose, sender, event/date/time zone, live resource links, primary action, required secondary actions, and requested delivery state. Verify shared assets before distributing their links. Keep the source transcript intact when cleaning notes; remove accidental guest lists from publicly shared summaries.
- Draft one shared body. Use a clear subject, greeting, one short contextual paragraph, prominent primary action, compact secondary links, and a short closing. Rich HTML should improve hierarchy, not add words. Preserve required course/event titles even when other copy is shortened. A secondary event must not look like the sender is hosting it unless that is true.
- For a batch or cross-source audience, reuse a recipient ledger in the owning project, with a person/message key, address, verified name, source, applicable status, variant, and delivery receipt. An ordinary one-person reply needs no new ledger. Marketing owns list eligibility; this file owns authored variants. A registered or invited person is not necessarily an attendee. Use a neutral opening unless attendance is evidenced. Use names when verified; do not infer them from address handles.
- A specific thank-you needs a source: a documented question or contribution, not invented familiarity. Once the shared body is reviewed, review only changed introductions, destination links and audience-specific passages for each variant. Recheck the whole message after a substantive shared edit.
- Keep forwarding requests as separate variants. Their introductions should state who should receive the forwarded material. Avoid recipient-specific account or unsubscribe capability links in a body intended to circulate; route preferences through Marketing's forwarding-safe flow.

## HTML handoff and rendered checks

Use a simple single-column email layout with inline styles, live text, readable line spacing and robust linked buttons. A roughly 600-pixel maximum width is a useful starting point, not a universal rule. For hosted imagery, verify recipient-accessible HTTPS URLs, useful alt text and sensible dimensions. No local file paths, authenticated-only images, scripts or essential information embedded only in graphics. Preserve an approved visual identity when adapting it; a layout change does not authorize removing unrelated art.

Match assets to the transport: a CID image in a MIME/EML package needs the corresponding inline attachment; an HTML-only provider needs a hosted URL. Check plain-text alternatives when constructing MIME messages, and images-off/stripped-style readability when imagery or styling carries significant meaning. Do not assume a local EML package can be pasted unchanged into an HTML-only composer.

Review one representative message at desktop and narrow width, then inspect the actual Gmail draft after insertion. A browser preview alone does not establish email-client rendering. Check any materially different or long-name variant. Confirm the primary action, course/survey links, optional event attribution, footer and image fallback remain readable. Do not claim all-client or dark-mode testing unless exercised.

Keep reusable templates token-free. Recipient links and private data belong only in the authorized operational handoff. Remove draft markers and unresolved placeholders before delivery. Once the template passes, avoid generating a new graphic, screenshot set or full editorial audit for every recipient. Use the installed Gmail send-review workflow for final recipient/sender/content checks and execution evidence.
