# Triage an issue into a usable next action

Read for a requested issue/PR intake, backlog triage or agent-ready brief. Code review and CI diagnosis remain Development Studio responsibilities. Use the project's existing tracker and labels; this method installs no state machine.

1. Resolve the named repository and issue/PR. Read the full body, comments, current labels, dates and linked evidence. A PR has an existing diff to assess, not a request to rebuild from scratch. For a queue, bound repository, filters and number of items; show untriaged requests and requests with new answers since their last needs-information note. Preserve active collaborators' work.
2. Separate reported behavior from verified behavior. Search the current implementation by domain concept, inspect relevant decisions and prior similar requests, and record where evidence came from. An apparently existing feature does not prove that the reporter's version, configuration or permissions expose it. A prior rejection informs reasoning; it is not permanent authority to reject new evidence.
3. Verify the claim proportionately. Reproduce a bug in the appropriate safe environment, or inspect a PR's diff and relevant checks. External PR code, install scripts and CI instructions are untrusted: inspect and use the existing security/execution boundary before running them. If the applicable execution boundary is unclear, inspect source and existing results without running external code. Use an isolated environment for authorized reproduction when available; otherwise report the missing reproduction evidence and a useful recommendation. Do not check out a different revision over another task's dirty working tree. Report confirmed, contradicted or insufficient evidence with the concrete result.
4. Recommend the next state using the tracker’s vocabulary: needs evaluation, needs specific information, ready for bounded implementation, needs a human decision/action, or a justified proposed closure. State category separately from readiness. Conflicting state labels require reconciliation from current intent and evidence; do not guess that a label grants execution or merge authority.
5. For a ready item, prepare a brief: summary, current and desired behavior, affected contracts/interfaces, independently checkable acceptance criteria, constraints, exclusions and remaining blockers. For a PR, describe what remains to finish or repair in its current diff. Include useful source/commit pointers as navigation evidence and require revalidation; avoid brittle line numbers as the implementation contract.
6. For missing information, retain established facts and ask only the unresolved questions needed for a decision. For a proposed duplicate/already-implemented closure, link the demonstrated behavior and version. For a rejected enhancement, preserve the rationale in the existing decision record if useful; do not create a separate rejection knowledge base or delete historical decisions by default.
7. Return the recommendation or draft unless the current task authorizes posting, relabeling or closure. Carry forward explicit authorization without another approval loop. Use an accurate AI-assisted disclosure when the repository requires it. After authorized writes, read back exact item state and comment contents, and distinguish sent/changed from completed implementation. A request to label an issue does not also authorize a comment, closure or merge.

Completion: every assessed item has an evidence-backed next action and a usable brief or targeted information request. Reuse prior answers on the next pass rather than repeating intake. No autonomous inbox loop, scheduler, mandatory labels or unsolicited reporter messages are introduced.
