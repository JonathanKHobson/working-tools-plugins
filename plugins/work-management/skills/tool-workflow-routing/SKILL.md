# Tool workflow routing

For “what can Work Management Studio do?”, setup or getting-started help, read the capability, first-task and setup sections of the [plugin introduction](../../README.md) and recommend one relevant first task; skip maintainer notes unless updating the package. Help alone does not start a diagnosis, scan, audit or external action. For a concrete request, use the matching procedure below without loading the whole plugin.


Choose the owning skill, app or MCP for a concrete task and resolve provider overlap or missing capabilities.

Consider the existing Compasses when the requested outcome is an interface evaluation, an argument/document critique, or prompt diagnosis. The user need not know or name the tool. Use the task cues in [MCP use check](../../references/operations/mcp-use-check.md#compass-selection-cues), select one relevant owner, and verify its current callable tools. For an already authorized review, a bounded check can proceed within that scope. When a scored report, council or guided checkpoints would expand the work, explain the concrete benefit and offer that depth at a natural decision point; preserve the user's answer rather than repeating the offer. A capabilities/help question stays informational.

## Workflow

1. Start with the requested output, its native goal and current evidence. Proactively use the smallest relevant installed plugin/skill; the user need not name it. For every new or continued project, consult `work-management:project-structure` at the start and when scope changes, reusing architecture already read in the current context. Find a matching owner in the maintained routing map only when ownership is unclear.
2. Read the chosen owner only; discover the actual tool before promising execution. Use the MCP check when tool exposure or connectivity matters. For substantial independent work, route through `worker-delegation` and verify the chosen model/mode. Deeper research defaults to standard ChatGPT Web in Pro mode when available; the special Deep Research feature requires an explicit request for that feature.
3. For a demonstrated recurring gap that existing methods and callable providers do not cover, use [find-skills](../find-skills/SKILL.md). It searches external sources, requires Master Security Toolkit admission review and integrates into an existing owner first. A broken connection or stale catalog calls for repair, not a duplicate plugin.
4. If an owner is wrong, hand off the existing facts and required result to the correct one without starting a second competing workflow.

## Deliver and verify

State the selected owner, usable capability and specific blocker if any. An installed skill, authenticated app and successful operation are distinct.

## Example boundary

Good: Survey owns the instrument; Writing edits wording within its constraints. Bad: launch every research or design plugin because their names match.

## Interactive work surfaces

Kyle prefers interactive panels when they make browsing, filtering, comparing, selecting or adjusting an output easier. Proactively use an existing task-matching MCP App or interactive panel for these jobs: scoped Atlas activity/framework libraries, UX-method comparisons, prompt-pattern selection, design options, or useful data controls. Use the owning studio and its actual callable capability; an ordinary short answer does not need an app.

Use visual questions when a diagram, process view or side-by-side comparison makes the decision easier to understand. Curate a small meaningful choice set, explain tradeoffs and recommend an option before asking Kyle; retain a freeform alternative or rejection. Use a large searchable gallery for exploration, not by default for a focused decision. Confirm the chosen answer through the supported handoff, and fall back to the normal question tool when needed.

Prefer an existing panel before building a new interface or adding a provider. If a requested output needs a new interactive surface, route to the existing UX Design or Data Visualization owner and the installed app-building capability as appropriate. Keep the domain's source, privacy and action boundaries; a panel is not permission to broaden retrieval, publish content, send messages or perform writes automatically. Give important results and action receipts in the conversation as well. For a site with unresolved audience, branding or visual direction, route decision intake and visual reference comparisons to UX Design’s product/web procedure; use its existing template gallery when applicable. Two-way input requires verified shared state or an explicit acknowledged selection handoff, not merely visible controls.

Distinguish an embedded MCP App, a local HTML preview and a hosted shareable. Check what the current host actually renders, use a local preview when needed, and state the real surface rather than promising unsupported embedding. User-confirmed visibility is valid evidence of visibility; it does not prove controls or write actions were tested. Do not make Kyle debug the host to finish a routine task. External shareable requests still follow the shared-site rule below.

When a Site offers a new or updated download, use the [download-hosting rule](../../references/operations/download-hosting.md) for the file destination and link verification; Sites still owns the page and deployment workflow.

## Sharing an idea versus creating a website

Kyle’s default for “share this idea with someone,” “give this idea to someone,” or a shareable web artifact is `work-management:work-handoff` and its [shared-site procedure](../work-handoff/references/shareables-site.md). Resolve the existing Shareables site before invoking Sites; add a page and homepage entry. “Create an independent website about…” explicitly selects a separate site. Preserve an explicitly requested email, message, file or other format. Artifact creation and sending it remain separate actions. Personal routing lives here; use the managed Sites plugin unchanged for its current construction, access and hosting tools.
