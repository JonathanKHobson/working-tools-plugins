# Hand off a reusable package across studios

Use when the requested deliverable is a reusable kit, template family or system assembled from multiple owners. For a one-off artifact, use the ordinary phase and editability handoff. Extend the existing project manifest or delivery note; do not create a competing registry, brand authority or mandatory document set.

## Bind the selected sources

Record only the sources actually used: owner, stable selected ID, version or digest, authoritative source path, intended role and permitted changes. A link without its selected revision is not enough to reproduce a release. Keep these roles distinct:

| Role | Existing owner | Preserve in the receiving work |
| --- | --- | --- |
| Audience, positioning, message and supported claims | Marketing Strategy | Adopted decisions, evidence, explicit unknowns and claim limits |
| Approved identity and retained brand source | Graphic Design / Brand Templates | Mark and asset variants, rights, token meanings and source authority |
| Visual artifact structure | Design Templates | Selected DESIGN.md, layout rules and native source |
| Voice, tone, style and format | Writing Templates / Writing Quality | Selected axes, exceptions, fact protection and audience needs |
| Component behavior and design/code mapping | UX Design Systems, then Figma or Development | Actual IDs/exports, states, adapters and adoption evidence |
| Motion, media and production source | Video Templates / Video Production | Selected style, timing, editable master and media rights |
| Evidence, learning or facilitation | Research / Data Visualization / Instructional / Workshop owner | Source meaning, uncertainty, objective, practice or facilitation behavior |

Omit unused roles. A library selection does not overrule the user brief. When two selected sources conflict, identify the exact conflict and authority before dependent changes. Reconcile semantic roles locally; do not rename all source tokens or impose one brand style across unrelated artifacts. Do not turn a project choice, research proposal or historical test into a universal standard.

## Declare the intended use

State the recipient, next task, target application/platform and version when relevant, required dependencies, editable master, generated renditions, rights and access. Distinguish a clean starting template, a populated example and author guidance when all are needed. Each may share a file if its role is unmistakable. An example containing fictional data remains an example.

Use a small core contract (identity, owner, source revision, purpose, inputs, outputs, dependency/rights, evidence) plus applicable type-specific checks. Avoid requiring identical folders or metadata from a writing method, component library, deck and video project. Existing manifests and source registers remain authoritative; optional machine-readable summaries point to them rather than becoming a second truth.

## Verify the delivered package

Test the actual final archive or delivery copy from a clean location, within authorized tooling. Resolve its internal references, fonts, data and media without relying silently on the creator's working directory. An intentionally remote service is a declared dependency, not automatically a packaging defect. Restricted assets may be omitted with their replacement/access instructions; do not redistribute them to make a package look complete.

Perform one meaningful recipient task, then save and reopen when the claim depends on persistence. A reusable family needs a representative case with different content or context; a copy of the original populated example does not test adaptation. Apply only relevant checks:

| Output | Revealing recipient task | Evidence needed for the claim |
| --- | --- | --- |
| Document/presentation | Create a page/slide, replace a long heading and image, reapply the declared style/layout | Native structure and editability in the target app, reading order, rendered export |
| Spreadsheet/data report | Replace representative input and check formulas, units, missing values and chart/caption relationships | Preserved calculation and meaning, with readable actual output |
| UI kit/site | Adopt in an isolated consumer and exercise a consequential state | Real imports/assets, behavior, accessibility and rendered viewport |
| Catalog/directory | Follow each in-scope source ID through the actual grouping/filter states to its visible entry and destination | Per-ID rendered discovery and destination evidence, with intentional exclusions explicit; inventory or match counts alone do not prove visibility |
| Writing/content kit | Adapt to a new audience and format while preserving verified facts | Explicit voice/format choices, source claims, meaningful variation and writing review |
| Video/interactive media | Reopen source and change a consequential timed/interactive element | Relinked media/fonts, editable source, playback and exported result |
| Learning/facilitation kit | Follow one participant task using the delivered materials | Understandable instructions, accessible participation and observable success criteria |

Use the existing [editability method](editability-handoff.md) for object-level claims. Record source and test identity, target environment, observed result and scope. Keep **implemented**, **checked structurally**, **rendered**, **behavior tested**, **recipient tested** and **published** distinct. Missing target access means that check remains unverified; it does not erase valid source work or authorize a substitute provider or installation.

Keep failures with the responsible owner and next concrete action. Passing this handoff does not prove every format, component or user journey, nor does it authorize sending or publishing.

## Basis and limits

This is an internal workflow convention generalized from reusable brand/template production research and the existing editability handoff. It is not an external certification or measured productivity claim. The release audit retains the source packet hashes and adaptation evidence. Provider-specific requirements remain with their owning methods and current documentation.
