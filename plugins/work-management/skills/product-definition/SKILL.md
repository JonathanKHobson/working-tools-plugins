# Product Definition

When orientation helps, briefly name this skill’s outcome, needed input and expected result, then proceed. Broader help uses the [plugin introduction](../../README.md); skip maintainer notes unless needed.


Match the output to the job. A terminology question needs a term and a plain definition; a fuzzy feature needs a buildable slice; a release decision may need a PRD or rollout plan. Do not make every request a full document. Start with the user, their painful moment, current workaround, intended outcome, and constraints. Separate observed evidence, assumptions, and open questions. For a beginner or AI-built app, use the optional [beginner discovery](../../references/beginner-discovery.md) when the problem or first slice is unclear.

For a short developer translation, name the term, platform context, behavior, and a ticket-ready sentence. For a feature brief, identify entry point, main flow, inputs, rules, permissions, meaningful states, dependencies, and observable acceptance criteria. Keep requirements tied to the user outcome. A proposed UI is not itself proof of the need it serves. When planning rollout, include data, privacy, failure, monitoring, and recovery decisions only where their absence would change delivery.

Use [spec shapes](../../references/spec-shapes.md) to choose a one-page brief, feature spec, change record, or fuller PRD. For a formal PRD or traceable change packet, load only the needed [PRD library](../../libraries/prd-strategist/references/workflow-and-artifacts.md) and its [template guide](../../libraries/prd-strategist/references/prd-template-guide.md); the staged [change-packet script](../../libraries/prd-strategist/scripts/create_change_packet.py) is optional. For exact terminology, use the [discipline glossary](../../libraries/plain-to-dev/references/discipline-glossary.md) or [component glossary](../../libraries/plain-to-dev/references/component-glossary.md). Use [reasoning check](../../references/reasoning-check.md) to test a load-bearing claim, then return to the product decision. A full reasoning audit belongs to Critical Compass. Use the owning document, UX, research, or engineering skill for a requested final format or deep specialist work.

Make the next build or validation step concrete. Do not silently implement, publish, message stakeholders, or create project scaffolding just because a plan recommends it. If implementation was explicitly requested in an owning project, continue through the authorized build and verification rather than stopping at the brief.
