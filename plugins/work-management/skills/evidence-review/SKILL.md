# Evidence review

When orientation helps, briefly name this skill’s outcome, needed input and expected result, then proceed. Broader help uses the [plugin introduction](../../README.md); skip maintainer notes unless needed.


Use an explicit manual checkpoint for a named project and selected source range. A finished reply, idle application or closed chat is not permission to collect its history. Help the user nominate meaningful feedback or decisions even when keywords miss them. Keep the records in the owning project's private evidence area; this plugin owns the review procedure, not project facts.

Read [the operating contract](references/operating-contract.md) before nomination or review. Use the bundled Python helper for validation, human dispositions and confirmed private saves. It processes only supplied excerpts and never fetches a reference, launches a model, reads history, updates memory/profile/skills, publishes, deletes originals or installs a hook.

A candidate needs a consequential event, constraint, decision, failure or learning and a traceable contribution, not just a word such as “after.” Separate self-report, inspected artifact, test report, inference and measured outcome. Preserve explicit negation, source origin and contrary sources. Hash agreement is byte consistency, not source truth or independent corroboration. Summaries sharing an original do not become independent witnesses.

Show the proposed claims, allowed wording, prohibited wording, missing proof, destination, retention owner and separate sharing permission. A human may hold, reject, supersede or accept individual bounded claims. Downstream use must select only `accepted_claim_ids`; card-level acceptance does not approve held claims. Acceptance needs explicit human confirmation and the helper's evidence gates; it does not make a record public-ready or publish it. Do not fill a human review from an AI judgment and call it human approval. Only use confirmation when the user has actually authorized that concrete review or save; existing session authorization can cover a specific held save.

Route reviewed statements and caveats to the existing portfolio owner when requested. Recurring procedure changes are proposals to their existing skill owner, and durable preferences require the host's permitted memory procedure. Do not create another plugin, hook or portfolio site as a side effect.

Useful requests include “review these selected corrections for case evidence,” “make one claim card from this checkpoint,” and “save this reviewed card privately.” Explain missing information with `[MISSING INFO: ...]`; preserve uncertainty instead of inventing methods, metrics, authorship or rights.

For a deliberately selected skill/plugin ecosystem release or cross-conversation evolution checkpoint, read [release evidence and provenance](references/release-evidence-and-provenance.md). It keeps deduplicated source identities, baseline/current/delta, state and measured-time boundaries in the owning project; it adds no watcher, automatic history retrieval, new catalog or publication permission.

For a selected correction, bug/barrier, task learning or worker insight—or a meaningful closeout under an existing learning-capture authorization—read [feedback to method review](references/feedback-to-method-review.md). Keep source, owner, task fix, transfer decision and validation/rollback linked in the existing project record. Complete authorized reusable improvements through their owner; otherwise leave proposals. No automatic session collection, memory write or human claim acceptance is implied.

For an authorized existing backlog inventory, Obsidian pointer index or publication/contact handoff, read [corpus and publication handoff](references/corpus-and-publication-handoff.md). Preserve originals and independent claim, retention, rights and delivery states; route the result to existing owners rather than creating a scheduler or automatic capture hook.
