# Feedback to method review

Use this procedure for an explicitly selected correction, review exchange or task artifact, or a meaningful task closeout when the user has authorized learning capture. Select only consequential feedback, task learnings, bugs/barriers or worker insights already available in the current task; record the selected range and authority. A standing learning-capture instruction is not permission to collect all messages or modify every related owner. Do not watch other sessions, scan private history, create a global observation log, schedule recurring review or write memory as a side effect. The [manual evidence card contract](operating-contract.md) governs private capture and claim acceptance when a card is actually requested.

## Separate the correction from a method

1. Identify the concrete failure or successful technique, its source and what changed in the immediate task. Fix the current deliverable within its existing authorization first. A correction to this result is not automatically a standing preference or skill instruction.
2. Test transfer: would the lesson apply to another task under the same owner, and does it name a repeatable decision, step or check? Look for a missing method, a bad assumption, a recurring failure or a simpler proven path. Leave one-off facts, temporary constraints, client details and tool outages with the project.
3. Compare the candidate with the exact current owner and its nearby method before proposing text. Record where the rule already exists, whether the failure was omission, routing, execution or evidence, and whether the apparent pattern repeats the same earlier finding. Do not add a second generic instruction when the real gap is an unenforced step or a broken provider.
4. Write one bounded proposal: trigger, action, evidence threshold, owner, acceptance check and what existing text it would replace or clarify. Preserve the selected source locator and uncertainty. A second observed failure of a written rule calls for investigating a practical verification barrier or workflow change; it does not by itself authorize a hook.
5. Present the concrete proposed change and its evidence. When the user has already authorized this scoped method improvement, complete it through the owning skill's maintenance workflow without another approval loop; otherwise leave it as a proposal. Route durable preferences through the host's permitted memory procedure and case facts to the project. Authorization to implement a method does not constitute human acceptance of evidence-card claims, permission to write memory, or public sharing approval. If no transferable improvement survives, record that outcome and stop.

Example: A user corrects an unsupported portfolio outcome claim. Fix the page, then check whether the portfolio owner already requires source-backed outcome wording. If it does, inspect why that check was missed; propose a concrete claim-verification step only if the selected evidence shows a recurring execution gap. Keep the particular case's metrics and people in its project record.

## Close the learning loop

Use the existing project evidence or decision record, not a new cross-project catalog. At a meaningful checkpoint, select up to three consequential signals; a trivial exchange or a checkpoint with no useful signal needs no record. Several restatements of one incident count once. The record can be a short Markdown entry; formal claim cards remain optional and retain their separate human-acceptance gates.

For each selected signal retain:

- **Source and observation:** stable lesson ID, exact message/file/receipt locator and revision or hash, author/model, evidence kind, and the observed event. Keep an exact user quote only if supplied; distinguish a paraphrase from a quote. Separate the proposed explanation and contrary evidence from what was observed.
- **Immediate task:** correction, workaround or unresolved barrier and its actual proof. Route an unresolved bug to the existing project issue/decision record; do not turn a provider outage or case-specific dependency choice into a universal rule.
- **Owner and transfer:** existing plugin/skill and exact method location, what it already covers, gap type (method, routing, execution or evidence), another applicable situation, and the strongest simpler alternative. Repeated summaries are not recurrence; a second independent application can support transfer but is not a numeric promotion rule. A demonstrated missing general check can justify a narrow change without waiting for a second failure.
- **Disposition and closure:** task-only, reuse-existing, proposed, applied-unverified, verified or reverted; a reason and next evidence needed. For a change, include current authorization, precise diff or changed location, pre-change revision/backup, targeted validation receipt and rollback. Verified means the changed procedure passed its relevant check, not that every future use or real-world outcome is proven.

Fix the current task first. Reuse an adequate existing method without adding prose. For an execution failure, investigate the practical barrier before duplicating a rule or adding a hook. Apply an authorized transferable change through the existing owner's maintenance workflow. Check a representative use and a bypass/negative case when routing changed; check the affected runtime when code changed. Test failure or incomplete evidence leaves it applied-unverified, or revert the owned patch if it causes a regression. Preserve the failed result and chosen disposition. Do not revert another chat's changes; if the owner changed meanwhile, reconcile the specific diff before applying or rolling back.

Treat Claude and other worker output as attributed advice. Record the actual model and response receipt, its supplied-source lineage, the lead's source check, and which suggestions were adopted, rejected or held. A worker repeating a test report is not a rerun, independent corroboration, human approval or proof of a working product. An unavailable source stays a gap. Record stale source versions and recheck before a consequential promotion.

Method improvement authorization, private capture, human claim acceptance, memory retention and public sharing remain separate. The workflow may complete an already-authorized reversible owner improvement without another approval question; it may not infer those other permissions. Reuse the existing nomination/validation tool for selected case-study claims; leave claims held until an actual human decision. Never promote a learning disposition into an accepted portfolio claim.

The existing work-start reminder can route the owning agent here conditionally. It must remain fixed context only: no transcript reads, content classification, private writes, model launches, new Stop continuation, or automatic self-modification. Prefer the bounded closeout above to another hook. This loop improves selected methods across tasks; it does not promise exhaustive capture after every interaction.

## Selected visual iteration checkpoints

When the selected exchange concerns an iterated visual, preserve the reasoning sequence alongside the final file in the owning project. Reuse its existing evidence record; a new tracker or formal claim card is not required unless requested. Capture:

- The visual's communication job, audience and intended placement.
- Each consequential version, source locator and actual maker/tool contribution; distinguish proposed techniques from executed work.
- The user's exact criticism or acceptance, separately from the reviewer's observed artifact diagnosis.
- What changed in meaning, composition or construction, why it changed, and which rejected properties the next version addressed. Check implied claims in visual marks as well as visible wording.
- The exact accepted artifact, retained imperfections, and rendered checks at the intended size and destination. Asset acceptance, integrated preview, scheduling and publication remain separate states.
- Outcomes still untested, such as comprehension, engagement or SEO. Do not turn a single accepted style, silhouette or provider into a universal rule.

Route repeatable production lessons to the design/image owner and capture lessons here. Record an explicit reuse/no-change disposition for adjacent skills when their existing method already covers the need. Keep the case's people, files and chronology out of generic skills. This checkpoint shape comes from local visual-production review; it does not alter the human claim-acceptance or sharing boundaries above.

## AI-assisted UI correction checkpoints

When the selected exchange concerns an AI-assisted UI correction, preserve the sequence in the owning project's existing evidence record:

- Separate the human's behavior intent from the assistant's inferred defect; record the mistaken mutation and the user's correction.
- Record restoration to the intended behavior before any later refinement, then distinguish that separately authorized refinement from the correction itself.
- Capture original screenshots at meaningful points, with editor context and relevant values when they explain the change. Do not reconstruct missing before states or treat screenshots as runtime verification.
- Identify the exact final artifact and verify that artifact in its actual intended context. Keep delivery to a curator, ingestion or acceptance, and public availability as separate states.

For example, an assistant may mistake an intentional transient overlap for redundant UI and hide it. Preserve the user's explanation that timing differs from a persistent field error, restore the intended overlap, and document any separately authorized styling refinement. Do not generalize the one case into a blanket UI rule.
