# Release evidence and provenance checkpoints

Use this conditional procedure for an explicitly selected skill/plugin release, migration or ecosystem evolution checkpoint. The existing [operating contract](operating-contract.md) and evidence-review helper govern nomination, held claims, human acceptance and private retention. This method is not collection permission. Keep project facts and receipts in the owning project's private evidence area; do not build a shared source catalog, another plugin, watcher or automation.

## Select the checkpoint

Name the owning project, purpose, session/revision, baseline and cutoff with timezone, precise source ranges and actual authorization. A request to capture a private candidate can authorize a held save; it does not supply human claim acceptance or public sharing permission. Use current project artifacts and supplied release receipts first. Retrieve other conversations or another computer only when explicitly in the requested range and actually accessible; record unavailable remote research as pending. A pending source is not a zero result, reviewed evidence or an installed capability.

## Source identity and state

Deduplicate publisher sources by normalized origin/repository plus commit/version and original method path. Store whole-file/excerpt SHA-256 and exact receipt locations. Separate identity (same source family), revision (changed source content) and copies/adaptations (many destinations of one original). Repeated heads, summaries, mirrors or packages sharing an origin are not new independent sources. A local original with no upstream revision can use a retained content manifest; mark its license unknown rather than inventing rights. Record selected portions and missing dependency closure precisely.

Use separate state fields rather than a single integrated label:

- considered: selected discovery/source metadata was examined; name exactly which files.
- adapted: a concrete scoped method/change exists at a target; identify changed text, steps and host boundaries.
- preserved: retained original method/support matches its source/hash mapping; identify complete versus selected-subset coverage.
- active: a maintained runtime head demonstrably routes to the method; a copied archive alone is inactive.
- installed: native install/update receipt plus installed-file parity verifies delivery on a named host/version.
- tested: name static link/schema checks, supplied-context model probes, protocol smoke, actual native runtime or deliberate user journey separately. A static method is not an authenticated provider or tested runtime.

Record original license/notice and private data limits. Source admission, private integration, public redistribution and publication have distinct gates. Unknown rights keep sharing held. Preserve historical/private originals; portfolio artifacts use reviewed/redacted derivatives.

## Baseline, current and delta

Freeze reproducible snapshots of the deliberately selected files and their hashes. Count definitions must travel with values: maintained owners, runtime discovery heads, unique source families, selected original methods, supporting files and tested workflows are different quantities. Exclude archived SKILL.original/LEGACY files, inactive source procedures, mirrors and host duplicates from runtime-head counts. Count one head by plugin-qualified path, not every Markdown file named SKILL.md. Compare matching scopes at matching host/time/revision boundaries. A staged added head is prospective until native installation and discovery verify; do not inflate installed totals with it.

Keep a compact provenance ledger with origin/revision, portion, considered/adapted/preserved/active/installed/tested, target, evidence receipt, source rights and unresolved proof. Show before/current/delta with scope changes and contrary evidence visible. Counts indicate coverage/maintenance surface, not quality, adoption, correctness, economic value or impact. Claim improvement only from the relevant outcome or behavioral evidence.

## Time and contribution

Record observed timestamps and their clocks/timezones separately from estimates. Use measured start/end boundaries for elapsed wall-clock; sum overlapping workers only for labeled aggregate worker time, never for human effort or elapsed time. File modification times and AI tool duration do not establish human time. Mark unknown active effort, wall-clock start, historical baseline date or cost as missing; do not invent saved hours. If the user supplies an estimate, retain source/range/method and label it estimated. Attribute human scope/decisions and AI assistance only from traceable instructions/artifacts; preserved upstream authorship remains distinct.

## Before/after proof and handoff

For a visual/public before/after, record actual URL/file/revision, capture date, viewport/page and 3–8 inspected anchors; distinguish original captures from generated reconstructions. Never present a reconstruction as an original screenshot or a document extraction as visual acceptance. Earlier public Compass material and current Studios/Toolkits may have different purpose and scope; the existing portfolio owner resolves that history and publication narrative. Keep absent original captures and remote-computer evidence pending, not replaced with plausible illustrations.

Prepare minimal selected excerpts and scoped candidate claims, allowed wording, prohibited wording, contrary sources, missing proof and rights. Run the actual helper's nominate, validate and authorized private save commands. Leave claims held until actual human review; do not fabricate a human decision to pass gates. Public-ready/published states remain outside this helper. Give the portfolio owner the private receipt/ledger and exact unresolved proof rather than a finished success story.

## Verification and ongoing use

Re-run the selected snapshot script at the next authorized checkpoint, retaining the old immutable snapshot and recording changed hashes/states. Include source-to-target preservation, native installation/parity, fresh qualified discovery and tests as their own receipts when actually complete. The helper stores immutable candidate/review revisions; do not overwrite accepted claims with changing release data. Update the owning project ledger only for meaningful release checkpoints. Stop when the selected evidence is reproducible and claims/limits are reviewable; broader historical inventory is a separate authorized scope.
