# Model worker selection and provider ownership

Use an external worker proactively when a bounded independent output reduces lead work or improves a consequential result while the lead continues useful work. Keep simple or inseparable tasks local. Optimize the whole job: briefing, inference, transfer, checking and repair, not just the price or parameter count of one generation. Record measured usage when exposed; do not claim Codex token savings from the mere existence of an offload.

## Select the provider toolkit

Provider-specific execution lives in the installed toolkits. Resolve the named skill through current discovery, not guessed sibling cache paths. A missing toolkit is an explicit dependency gap, not a reason to reproduce its full manual here.

| Selected route | Toolkit owner | Initial task-fit hypothesis |
| --- | --- | --- |
| Claude CLI, Desktop or Web | `claude-toolkit:claude-operation` | Sonnet for well-specified work; Opus for ambiguous architecture or deep critique; actual versions must be verified |
| Gemini/Antigravity CLI or Gemini UI | `gemini-toolkit:gemini-operation` | Flash for bounded transformations; higher-capability Gemini for synthesis or another implementation perspective |
| DeepSeek through an authorized hosted endpoint | `deepseek-toolkit:deepseek-operation` | Provisional alternative for bounded code/reasoning, supplied-source critique or English–Chinese interpretation; verify current host readiness and outputs |
| Apple Foundation Models | `apple-foundation-model-toolkit:apple-model-operations` | Short local classification, extraction or rewriting, after readiness and quality tests |
| Downloaded local models | `local-model-toolkit:local-operation` | Privacy/offline or repeated narrow work where measured quality, latency and memory fit |

The toolkits own current model options, CLI-first procedures, UI exceptions, authentication and recovery. This file owns selection and the common handoff, not duplicated vendor catalogs. Work Management still owns goals, scopes, coordination and integration. Existing domain Studios retain the actual work: spreadsheets, research, 3D, writing and software need their domain tools and validation. No model is an inherent universal specialist; provider claims and benchmarks nominate trials, while actual task output decides.

## Concrete selection before implementation

For substantial work, name one independently checkable output and dispatch it before bulk lead implementation. Prefer an eligible subscription or local CLI worker for supplied-context work that does not need the lead's host tools. Native subagents remain suitable for shared host tools, narrow code ownership or visual sessions. These are choices within one goal, not a requirement to create a separate chat.

- **Gemma:** short supplied-text extraction into a schema, sorting/classification, a compact outline, a first draft or a focused snippet critique. Fit the host's tested context/output limit and current resources. Deterministic code/tests check its claims; the model is not a syntax checker. Do not load it for every prompt or rebenchmark an unchanged route.
- **Gemini:** bounded synthesis of supplied documents, structured format migration, proposed acceptance/test cases, or an independent implementation/design critique based on supplied evidence. Start with the verified Flash route for a well-specified task; use a verified higher-capability route when its depth is justified. Do not assume Google account access supplies Workspace or other host tools.
- **Claude:** Sonnet for a specified implementation, source-grounded analysis or code review; Opus for architecture, ambiguity and deeper critique. This does not exclude Gemini from code or Claude from synthesis.
- **DeepSeek:** an additional model family for a checkable alternative solution or source critique. Resolve the tracked helper through DeepSeek Toolkit and verify the endpoint's free allowance before use. Different output or national origin does not establish independent evidence, cultural authority or superior cultural perspective. Its text helper has no host tools.

Pick by evidence, tools, context and current availability, rather than choosing Claude by habit or filling a provider quota. A legitimate opportunity has a discrete output, sufficient authorized input and an acceptance check while the lead progresses separately. If a substantial task has none, briefly name the actual blocker (for example, every next step depends on the same live UI), rather than simply saying offload adds overhead. Low counters alone cannot prove missed opportunities. A successful worker return and checked integration are evidence of use; a hook reminder is only guidance.

## Learn from a strong component

Treat a useful model output as a task-specific reference, not a provider ranking. Name the component and why it worked, then request a bounded proposal or critique for that part. A comparison section, concise headline or responsive character interaction can transfer without importing the rest of its page. Keep the receiving project's content, brand and accessibility authority. Evaluate the result in its actual layout and state.

Choose implementation and review roles separately when an independent check would help. Give the reviewer the final render, selected source targets and strengths to preserve. A completed checklist or another model's agreement does not establish visual quality. Record the actual contribution, integration decision and check. Update task-fit guidance only as a bounded observation with its conditions and contrary evidence; one paired result cannot establish a general model advantage or plugin effect.

## Execute one useful handoff

Supply outcome, selected evidence, permitted tools/side effects, file ownership when relevant, checks, timeout and stop condition. Prefer CLI when it provides the needed capability; use UI when explicitly requested or for a verified interface-only feature. Check current service authorization, runtime, account and allowance. Model access does not imply access to Google Workspace, web browsing or the other host’s MCPs. Never enable paid APIs or extra credits as a fallback; no switching providers to evade a subscription limit.

Retain the active job rather than re-dispatching it. Record requested model/effort separately from returned metadata; self-reported identity is not verification. Check successful nonempty output, scope, source accuracy and relevant code/artifact tests. Use another model only for a distinct contribution or a diagnosed failure, not a mandatory second vote. Treat tool denials and partial output as incomplete even if a process exits zero.

For suitable short supplied-context extraction, classification, synthesis, drafting or small code review, proactively use the host’s verified default local route when its checks and current resource limits fit. Resolve its exact model and command from the host capability record; do not ask the user to choose again or rebenchmark unchanged capabilities. Keep trivial work direct and escalate failed acceptance checks without silently substituting another model. A default is a starting choice, not a guarantee or a reason to offload tool-dependent research.

For local benchmarking, use the local-model toolkit and the host’s measured capability record. Exact model, quantization, context, runtime and current memory matter. One local inference at a time; preserve other tasks’ jobs and unload only owned instances. The installed small model is a baseline, not a quality ceiling.

The existing context hook directs the lead to dispatch a useful bounded independent output on substantial work, while the lead continues disjoint work. Examples include supplied-context extraction, implementation review, source-grounded research synthesis and design critique. Do not replace actual delegation with a plan to consider it or wait for a per-task request. A simple or inseparable task can stay local; there is no minimum call quota. It must not automatically launch models, download weights or consume quota on every user prompt. Keep available-versus-verified distinctions in the owning host record and refresh on actual capability changes or failure.

## Optional measured use

When the receiving host explicitly opts into private usage tracking, use the instrumented provider toolkit wrappers by default for delegated CLI work without a per-task tracking request. Use direct CLI execution only for diagnostics or a needed capability not supported by the wrapper; record that coverage limitation. Never repeat an already completed model call only to obtain telemetry. These can emit metadata-only completion events through the host's `~/.config/studio-tools/usage-tracking.json` binding. Resolve its configured recorder; never invent a private storage path. Tracking must use no model calls, polling or persistent helper, and failure must not block the delegated task. Keep requested versus returned model, reported versus unavailable tokens, actual helper/MCP execution and unmeasured skill application distinct. Native post-tool coverage only includes exact mapped execution events, not mentions or opaque nested command text. Work Management owns the common recorder contract; provider toolkits own their execution boundaries. An opted-in local dashboard may receive deterministic completion notifications while open; that is distinct from launching models or polling. Do not infer account quota or token savings from offload counts.
