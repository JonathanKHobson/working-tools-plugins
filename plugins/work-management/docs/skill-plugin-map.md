## Merge and loading policy

Aim for 8–10 diverse use-case skills in a substantial Studio/Toolkit, more when distinct workflows warrant them. Split broad skills when a narrow request would otherwise load unrelated methods. Keep every unique workflow, good/bad example, template, exception, check and useful support asset. Condense repetition or remove exact duplicates with a source-to-owner record; never replace full source skills with topic summaries. Give each skill a precise trigger and relevant delivery/quality checks. Shared complete sections may be conditional references. Do not pad counts with aliases or duplicated workflows.

Edit the canonical `~/plugins/<name>` owner, validate it, use native cachebuster/install tools and compare installed files to source. Verify hooks and real provider capability before retiring an old entrypoint. Existing chats may retain their initial discovery catalog; use a new chat after installation. Do not fix implementation by editing caches; compatibility launchers for old pinned hook paths are an explicit temporary migration measure.

Full source preservation and source adaptations are recorded in each owner and the private consolidation report. Nested source manifests, hooks and scripts are preserved for fidelity but are not automatically activated. Current user and host instructions govern old vendor promotion, unsupported detector claims, blanket approvals and obsolete commands. Preserve original notices; public redistribution needs a separate license/private-data pass.
