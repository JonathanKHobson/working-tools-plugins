# From intent to an implementation contract

Use for a software request whose ambiguity could cause either missing behavior or speculative features. Clear fixes and tiny edits proceed directly; no new PRD, file or approval ceremony is required.

Work Management owns the intended outcome, business scope, priorities, exclusions and consequential open decisions. UX Design owns the human-facing requirements when a person interacts with the result. Prompt Playbook owns instruction refinement when the prompt needs repair or is the deliverable. Development Studio owns code, dependencies, verification and the smallest complete implementation. These are responsibilities, not four mandatory sequential conversations.

Classify uncertainty from current evidence:

| Situation | Next action |
| --- | --- |
| Behavior and target are clear | Proceed through Development `implement-software`. |
| Details are inferable from established behavior or conventions | Infer routine reversible choices and state material assumptions. |
| A missing business fact or consequential choice changes the outcome | Resolve it from authorized sources or ask a concise question while continuing independent work. |
| The user outcome or useful slice is unclear | Use the existing Product Definition method to establish it, then continue the authorized implementation. |

In the existing conversation or project brief, capture: intended outcome and observable completion; required behavior and affected boundaries; applicable UX expectations; explicit exclusions; assumptions and unresolved facts; acceptance checks. A short repair may need only a sentence and its regression condition.

For human-facing work, route to UX `design-studio` and its `implementation-expectations` reference when available. Preserve content/behavior from the existing organization and design system. Identify what a person must understand, do, recognize as completed and recover from. Include relevant error, empty, pending, disabled and success states, keyboard/accessibility requirements and responsive contexts. These requirements complete the chosen task; they do not authorize new business capabilities or a redesign.

Distinguish expected quality from feature expansion. Clear plan prices, scope and a usable selection action support a pricing page. An annual-billing toggle requires an offering with annual billing. Do not infer testimonials, legal terms, analytics, checkout or additional tiers. A fictional prototype may use clearly labeled samples under the brief's authority.

When the contract is ready, hand it to Development Studio's efficient implementation method through `implement-software`. Minimize implementation complexity only after identifying the complete behavior. Do not demand another confirmation where current instructions and evidence settle the work.

Reopen only affected assumptions when new callers, risk, conflicting evidence or acceptance failures appear. Keep exclusions and declined features intact. If a companion plugin is unavailable, retain this contract locally and continue through the available implementation tools; a handoff is not an installation requirement.
