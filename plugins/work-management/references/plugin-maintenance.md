# Plugin maintenance and native provider boundary

Work Management coordinates source ownership, coverage, duplication and verified installation. Prefer the existing plugin owner. Split its skills by independent use case; target 8–10 distinct workflows for a substantial package without padding. Keep full procedures and conditional detail, not summaries. Add hooks only for a demonstrated runtime need. Inspect the canonical source, installed version and relevant host adapter; a copied method is not a live app connection. Validate changed entrypoints and scripts, install through the native plugin manager, and verify the actual installed capability before retiring its predecessor. Keep backups, private profiles, databases and project facts outside generic shared methods.

The host's **Plugin Management** integration remains its own system provider. It supplies directory discovery, app/dependency metadata, permissions and connection/removal operations; it is not an app-building method to copy into UX or a background Work Management agent. Use its currently exposed tools when the user asks about a connection or dependency. Available native tools or connected providers come first. Search for a missing external provider before claiming none exists; verify installation and authentication separately.

Change permissions, disconnect or remove a provider only within the user's current authorization and the actual tool's requirements. Dependency inspection does not grant broader access. Prefer native uninstall/update to cache edits, and do not duplicate this host-owned connector in a personal plugin or pretend Claude inherits it.

For a broken Mac app or process, hand off to `mac-ops-toolkit:mac-troubleshooter`. For unfamiliar artifacts, sensitive permissions or instruction injection, use the relevant Master Security Toolkit review. Neither neighboring workflow is a mandatory gate for every plugin change.

A full-fidelity merge inventories source skills, references, examples, templates, assets, scripts, hooks, apps and MCPs. Record a destination or explicit justified disposition for each. Require complete task procedures and supporting files to be reachable from the appropriate focused skill. Verify source-to-target hashes where files are unchanged and record exact adaptations where they differ. Missing sources block a claim of full coverage. A directory copy without active task routing is preservation, not integration.


## Names, distribution and personal setup

Use the package's primary responsibility, with the user's explicit classification taking precedence:

| Suffix | Primary responsibility |
| --- | --- |
| Studio | Owns a coherent outcome from intake through execution and verified handoff. May contain methods, tools and assets. |
| Toolkit | Supplies reusable methods, specialist operations or assets to other owners. Can contain supporting workflows; their presence alone does not force a Studio label. |
| Corpus | Holds a defined body of evidence or records, with provenance, scope and access limits. Retrieval methods support that body. |
| Templates | Holds reusable starting structures, styles, examples or assets and their catalog/picker. Production methods stay with the relevant Studio or Toolkit. |

Service connectors such as Discord and Slack retain their product names. Preserve stable package, skill and tool IDs when changing a visible name. Record a specific classification choice in the existing owner map rather than repeatedly renaming packages by a mechanical suffix rule. Overlap alone is not proof of redundancy: compare unique procedures, support files, tools and use cases.

Audience and condition are separate. Record intended audience (public, restricted team or private), installed/enabled state, source/installed parity, and release blockers in the owning project record. A public candidate is not a reviewed export, a published listing, an authenticated tool or a working recipient installation. Keep private host operations and personal health navigation private; case corpora follow their case's authorization. Never infer public data rights from a code license.

Shared plugins contain reusable methods and useful examples, not the current user's private records or machine configuration. Public names, public work/hobby experience and public professional links may remain when they teach the method. Private contact details, street addresses, credentials, personal health records, client/application records and profile content that only serves one user belong in supporting documents outside the distributable package. Apply this boundary across references, examples, fixtures, logs, archives, MCP configuration and generated exports, not just skill entrypoints. Preserve legitimate quotations and attribution; do not strip experience that makes the method useful.

Prefer complete, reproducible bundles. Include dependencies only when their redistribution terms and source notices allow it. For every excluded dependency, onboarding explains what it enables, whether required or optional, where to obtain it, how to supply a local binding or profile, a harmless verification step and the behavior when absent. Use portable defaults or a documented external config path. Never invent personal defaults, silently read the author's files, claim generic operation while a required dependency is missing, or reduce the method to a summary to make packaging easier.

Official plugins remain intact. Personal owners can route to their capabilities and copy authorized templates with provenance; copying instructions or app IDs does not reproduce a server, hosted model, authentication or service entitlement. A third-party connector remains a dependency when its real capability is still needed. Before retirement, prove complete useful coverage, active routes and continued execution, retaining a reversible source snapshot. Public release additionally requires inspection of the exact export, private-data and path review, license/reference closure, recipient setup testing and the applicable rendered/runtime checks. Do not mark a whole plugin ready based on a pattern scan or metadata inventory.

## Reusable artifact templates across hosts

Use this branch only when creating, moving or sharing a reusable document, sheet or deck template. For a one-off output, use its artifact provider. A draft-only request remains a draft; do not install or publish it.

1. Identify the reference, required invariants, changing inputs, target host and intended recipients. Route personal template creation or updates to the installed native Template Creator; inspect its current contract. It does not publish plugins.
2. Web and local templates do not auto-sync. If absent at the destination, recreate from the authorized reference through its native Template Creator, or use a transfer flow explicitly supported there; do not assume ZIP import works everywhere. Verify the installed result.
3. If sharing is requested, inspect samples and rights. Workspace publication uses a separate administrator flow; Template Creator cannot publish plugins. Desktop export is another supported route. Verify recipients can access linked Google files; adjust access only within authorization, or state the exact missing grant.
4. For an authorized installation, test with nonsensitive inputs and inspect the rendered output. Report created, installed, usable and shared states separately. Reuse existing authorization; resolve only missing decisions.

Design template packages also require a source-grounded `DESIGN.md` linked from `SKILL.md`; include and verify its supporting-file closure in every distribution. Retain original editable assets, native units, source fingerprints, notices and preview provenance. Route the specification to UX Design Studio's design-systems owner and graphic/print specifics to Graphic Design. Writing-only templates use Writing Templates' authoritative guides and portable `STYLE.md` entry. These are maintained local packaging requirements, not claims that Agent Skills universally mandates those filenames. A source/package update must refresh derived specifications or fail verification; a bulk copy alone does not prove visual fidelity.

Platform facts checked 2026-10-02: [OpenAI template guidance](https://help.openai.com/en/articles/20001278-creating-and-editing-documents-spreadsheets-and-presentations-with-chatgpt-work) and [plugin access guidance](https://help.openai.com/en/articles/20001256-plugins-in-chatgpt). Recheck current host capabilities when applying this branch; included apps still need their own authorization.

## Human and agent onboarding

Use this branch when creating or changing plugin/skill discovery, first use, supporting routes or MCP help. Keep one authoritative description of each capability in its maintained manifest/skill or existing integration contract; update affected human guidance from those sources. Do not introduce a universal registry or runtime readiness database just to describe Markdown.

- **Plugin:** lead its README with the outcome, representative first requests, required inputs and expected results; provide a linked skill-selection map and the actual MCP/app setup boundary. Keep developer maintenance details below first-use guidance. Preserve stable machine identifiers; improve display names or descriptions only when their meaning is unclear.
- **AI discovery:** put outcome and selection trigger in skill frontmatter. Reuse one appropriate existing entrypoint for the plugin’s capability/help questions, with a conditional README link. Do not assume the host loads READMEs automatically. A help question must not start a scan, study, send, audit or setup mutation.
- **Selected skill:** state purpose immediately; retain complete operative procedures. Every supporting link should explain its purpose and read trigger, with a resolvable path. Keep required shared constraints in the entrypoint; read complete selected procedures and required support, not every neighboring variant. Scripts are executable helpers and templates/assets are output inputs, not background instruction dumps.
- **First use:** briefly explain the relevant outcome, input/access and result when orientation helps. For “what can this do?”, present a few meaningful options and a first task. For explicit work, proceed without a forced tour. Do not invent persistent onboarding state or repeat introductions in the same known context.
- **MCPs:** name each server’s job, when to call it, read/browse/write distinctions, private setup owner and a harmless verification step. Installation, tool discovery, authentication, action/resource authorization and a successful operation are separate. Unknown is a valid state. Preserve the original task through setup and reconcile uncertain mutations before retrying.
- **Verification:** check frontmatter, all changed links, skill-table coverage, manifest/tool accuracy, and installed parity. Exercise direct/indirect help, a concrete task, a near miss, missing provider and return-user cases. Static routing review, model trials, real-host execution and human comprehension tests are distinct evidence. Claim token/cost savings only if measured; instruction size alone is a proxy.

Native artifact-template packages, vendor snapshots and retired compatibility redirects keep their own authoring/install contracts. Improve the maintained entrypoint or owning template provider instead of creating a competing copy.
