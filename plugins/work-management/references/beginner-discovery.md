# Beginner discovery, on demand

Use when a first-time builder has a fuzzy app idea, is frightened by a messy AI-built project, or needs the next build step in plain language. It is not a gate before a clear request. Match the user's experience level without making them complete an interview.

Find a specific person, the moment they struggle, what they do today, and what would make a switch worthwhile. Mark evidence as **seen**, **heard**, **hunch**, or **guess**. Public complaints and reviews suggest hypotheses; they do not measure prevalence or replace direct user observation. For two-sided products, identify the work and incentive on both sides. Pick a first version with one distinguishing value and the table stakes needed to use it.

Explain only technical choices that change the next action: where data lives, who can sign in, whether a service costs money, what can fail, and how the user can recover a working version. Prefer a concrete recommendation with one reason over a menu of stacks. Check current prices and free tiers before stating them. Make the riskiest assumption and a cheap test visible before a large build.

For an existing AI-built project, inspect the real repo and reproduce the painful path. Snapshot recoverably, fix one confirmed cause, then show the check. Keep the project navigable: one clear home for each feature and a concise map. Do not recommend a rewrite from the user's frustration alone.

The existing Vibe Check package has richer teaching diagrams, marketplace/cold-start material, and beginner checkup aids. Keep it as an optional specialist if that full experience is requested; this reference is a compact method, not a copied replacement. Do not route human prose or tone work through beginner app discovery.
