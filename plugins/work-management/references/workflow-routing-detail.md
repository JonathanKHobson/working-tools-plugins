# Tool workflow routing

For “what can Work Management Studio do?”, setup or getting-started help, read the capability, first-task and setup sections of the [plugin introduction](../README.md) and recommend one relevant first task; skip maintainer notes unless updating the package. Help alone does not start a diagnosis, scan, audit or external action. For a concrete request, use the matching procedure below without loading the whole plugin.


Choose the owning skill, app or MCP for a concrete task and resolve provider overlap or missing capabilities.

For substantial work, translate the user's intent into a compact acceptance contract using Prompt Playbook's `prompt-refinement` ambition method when needed. Route by the accepted outcome and observed gaps, not a keyword quota. Select one production owner, then only the contributors and reviewers the actual deliverable needs. Read the relevant skill entrypoint and triggered references, reusing context already loaded. Revisit the route when scope changes.

If the host truncates its skill catalog, absence from the visible list does not establish that a capability is missing. Use the maintained skill routing and studio ownership links below for the relevant family, then read the exact installed entrypoint. Pass that path to the worker who needs it. Do not load whole catalogs or install a duplicate to compensate.

For any authored reader-facing deliverable, `writing-quality-studio:natural-prose-editor` owns the everyday Humanizer pass. UX owns information placement and interface states; Prompt Playbook owns intent translation; Work Management owns assignment and evidence handoff. A skill read, hook reminder or tool call is not proof of a completed review. Keep recorded editorial attestations distinct from observed tool usage.

Consider the existing Compasses when the requested outcome is an interface evaluation, an argument/document critique, or prompt diagnosis. The user need not know or name the tool. Use the task cues in [MCP use check](operations/mcp-use-check.md#compass-selection-cues), select one relevant owner, and verify its current callable tools. For an already authorized review, a bounded check can proceed within that scope. When a scored report, council or guided checkpoints would expand the work, explain the concrete benefit and offer that depth at a natural decision point; preserve the user's answer rather than repeating the offer. A capabilities/help question stays informational.

## Workflow

1. Start with the requested output, its native goal and current evidence. Proactively use the smallest relevant installed plugin/skill; the user need not name it. For every new or continued project, consult `work-management:project-structure` at the start and when scope changes, reusing architecture already read in the current context. Find a matching owner in the maintained routing map only when ownership is unclear.
2. Before defaulting to a prose-only answer, consider whether an existing capability materially improves the task's understanding, comparison, exploration, editing or verification. Read the chosen owner only; discover the actual tool before promising execution. When it fits the current request and authority, call it rather than merely naming it or asking whether to use it. This check is quiet and does not require an inventory or visible checklist for every turn. Use the MCP check when tool exposure or connectivity matters. For substantial independent work, route through `worker-delegation` and its provider toolkits (Claude, Gemini, Apple Foundation Model and Local Model); verify actual readiness, selected model and useful output. These are available execution routes alongside plugins and MCPs, not automatic jobs on every turn. Deeper research defaults to standard ChatGPT Web in Pro mode when available; the special Deep Research feature requires an explicit request for that feature.
3. For a demonstrated recurring gap that existing methods and callable providers do not cover, use [find-skills](../skills/find-skills/SKILL.md). It searches external sources, requires Master Security Toolkit admission review and integrates into an existing owner first. A broken connection or stale catalog calls for repair, not a duplicate plugin.
4. If an owner is wrong, hand off the existing facts and required result to the correct one without starting a second competing workflow.

## Software artifacts and source questions

For a software build whose intent is unsettled, Product Definition's [implementation readiness](implementation-readiness.md) resolves the complete slice. Human-facing behavior uses UX Design's expectation handoff; a ready contract goes to Development Studio `implement-software` and its efficient implementation method. Prompt Playbook owns instruction repair, not routine product decisions. A clear bug fix or tiny edit goes straight to implementation. Review/audit/debt and benchmark questions use Development Studio's existing review/evaluation heads.

For a shipped app, native binary, package/bundle or version comparison, proactively select `development-studio:reverse-engineer-software` when the available source is absent or cannot answer the question, observed behavior differs from source, or an authorized reconstruction needs behavior evidence. The user need not say “REA” or “reverse engineer.” If the repository answers the question, select `development-studio:code-intelligence` and the existing implementation/debug/test owner instead. A screenshot alone supports appearance, not hidden implementation.

Pass the exact permitted artifact/version, bounded question, available source and requested output. Development Studio owns the existing REA method and complete 207-tool MCP surface; verify actual callable tools and its runtime contract before execution. Routing adds no plugin, hook, installation, target access, live capture or network permission, and does not replace native approval. If a required provider is unavailable, retain the question and report that specific dependency. Distinguish an absent MCP connection from an optional engine missing for one operation: continue supported static or source work with explicit coverage limits. A third-party artifact is eligible only when the task establishes authorized access; a routing decision does not supply that authority.

Receive scope, dependencies, evidence with coverage limits, unresolved questions and any rebuild acceptance criteria through the existing `product-definition`, `project-structure` or `work-handoff` workflow only when planning or coordination is needed. Continue one owning workflow; a return is not a fresh intake, automatic build or repeated handoff loop.

## Deliver and verify

State the selected owner, usable capability and specific blocker if any. An installed skill, authenticated app and successful operation are distinct.

## Example boundary

Good: Survey owns the instrument; Writing edits wording within its constraints. Bad: launch every research or design plugin because their names match.

## Interactive work surfaces

Proactively use an existing task-matching MCP App or interactive panel when browsing, filtering, comparing, selecting or adjusting is part of the user's task. The user need not ask for a widget or know its name. Pick the surface by the benefit to this task, not a quota for tool use. Honor plain-text-only, static-export and other explicit output choices. A simple fact, small correction or routine status answer usually stays in conversation.

| Task cue | Preferred existing route | What earns the surface |
| --- | --- | --- |
| Compare quantities, trends, distributions or uncertainty | Data Visualization Toolkit, appropriate chart method | A truthful chart reveals a relevant pattern or comparison more clearly than prose/table alone. |
| Filter a supplied table, inspect exact rows, retain a view for discussion | Data Visualization `interactive-explanations` and Data Explorer | Relevant source data fits the current tool limits; filtering or saved views are useful. Read/prepare data through the authorized source owner first. |
| Revisit multiple metrics to make repeated decisions | Existing dashboard and its data owner; `live-dashboards` for dashboard work | Known source, grain, refresh state and decision. A dashboard request does not itself authorize a recurring job or fabricated live feed. |
| Explain dependencies, sequence or a system | Structural diagram or interactive explanation | Use a static diagram for fixed structure; controls only when changing an assumption answers a useful question. |
| Human wants to browse or choose methods, activities, templates or design options | Matching Atlas/library browser or Framework Builder | Curated eligible options and actual human selection. For assistant-only retrieval, use search/read tools without opening a gallery. Follow builder-specific input/preview gates. |
| Inspect a completed evidence review and discuss findings | Relevant Compass owner and its review panel | The analysis exists and meets the panel's input contract. A display widget is not the analysis engine. |
| Edit or calculate in an existing sheet, document, slide or design | Native artifact/app tool for that source | Actual editable result and readback in the requested format. A prose description does not replace the edit. |

A request to understand change over time can merit a static chart even without a request for filters; lack of interactive controls is not a reason to return prose alone. When the user already wants to browse or choose, open the appropriate eligible gallery without another permission question. When the user wants the assistant to choose and return a finished result, use assistant-only search/read and deliver it; do not insert a builder or Copy/Send gate unless the provider's selected workflow requires it or the user wants to edit there.

For missing data or connection details, inspect the already-authorized source and native connection status first. Ask only for the consequential unresolved input; never ask for credentials in chat. An explicit monitoring request authorizes pursuing setup through the automation owner, while unresolved source/cadence choices still need resolution. Do not treat a static dashboard request as recurring-monitoring permission.

Select one primary surface initially; add another only for a distinct job. Briefly explain what it helps the user do and include the key result in chat. Retrieve narrowly, check source provenance and current tool limits, and avoid opening redundant panels or copying unrelated private rows. A tool description is a capability contract, not evidence the provider worked. If a useful surface is unavailable, name the specific gap once and continue with a suitable chart, table or direct answer; preserve the original task. Do not build or install a new dashboard/plugin merely because an existing tool is inaccessible.

Use visual questions when a diagram, process view or side-by-side comparison makes the decision easier to understand. Curate a small meaningful choice set, explain tradeoffs and recommend an option before asking the user; retain a freeform alternative or rejection. Use a large searchable gallery for exploration, not by default for a focused decision. Confirm the chosen answer through the supported handoff, and fall back to the normal question tool when needed.

Prefer an existing panel before building a new interface or adding a provider. If a requested output needs a new interactive surface, route to the existing UX Design or Data Visualization owner and the installed app-building capability as appropriate. Keep the domain's source, privacy and action boundaries; a panel is not permission to broaden retrieval, publish content, send messages or perform writes automatically. Give important results and action receipts in the conversation as well. For a site with unresolved audience, branding or visual direction, route decision intake and visual reference comparisons to UX Design’s product/web procedure; use its existing template gallery when applicable. Two-way input requires verified shared state or an explicit acknowledged selection handoff, not merely visible controls.

Distinguish an embedded MCP App, a local HTML preview and a hosted shareable. Check what the current host actually renders, use a local preview when needed, and state the real surface rather than promising unsupported embedding. User-confirmed visibility is valid evidence of visibility; it does not prove controls or write actions were tested. Do not make the user debug the host to finish a routine task. External shareable requests still follow the shared-site rule below.

When a Site offers a new or updated download, use the [download-hosting rule](operations/download-hosting.md) for the file destination and link verification; Sites still owns the page and deployment workflow.

## Sharing an idea versus creating a website

For a shareable artifact, use `work-management:work-handoff` and its [shared-site procedure](../skills/work-handoff/references/shareables-site.md) only when the user requested or explicitly configured that destination. Verify the existing site before creating a page. An independent website is a separate scope. Preserve an explicitly requested email, message, file or other format. Artifact creation and sending it remain separate actions. Use the current host's supported Sites capability for construction, access and hosting checks.
