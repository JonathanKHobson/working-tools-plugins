# Contact and recipient handoff

Use the receiving user's chosen private contact source. Resolve the current roster, stable identities, preferences, exclusions and delivery history before preparing a message. Keep these records outside shared plugins; the reusable method contains no roster or machine binding.

A request to inspect contacts is read-only. An explicit record-change request authorizes that scoped change; preserve stable keys and history, mark stopped entries inactive and resolve genuinely ambiguous identities. Updating a contact does not authorize a welcome message, enrollment or delivery. Keep dependent group/schedule references consistent only when the requested change requires it, preserving unrelated cadence and permissions.

Separate contact membership, user sending authority, recipient consent and actual delivery. Use only the authorized recipient set and sender, filter evidence for each recipient, and keep private context scoped to its intended reader. Preserve a draft hold. Use the current writing/provider review and native send/schedule readback when delivery is explicitly requested. Reconcile an uncertain result before retrying, and record prepared, scheduled, sent, received and read as distinct states.

The private adapter owns actual files, account bindings, mailing templates and provider receipts. Missing storage or provider access is a concrete dependency gap; do not create a replacement address book, invent contacts or claim delivery. This procedure creates no sender, scheduler or contact service.
