# Hosting downloadable files from Sites

Apply this forward-looking rule when a new or updated Site offers a downloadable package, archive, installer, binary, or substantial user file. Sites owns the page and the assets needed to render it, including previews and genuinely small downloads. Normally host non-tiny downloads outside the Site and link to the exact file. This is not a universal file-size cutoff.

For a public, reusable, redistribution-permitted package, prefer a versioned GitHub Release with a direct asset URL and recorded version and SHA-256 hash. Keep release binaries out of Git history. For a large user-specific or private file, use Google Drive when appropriate, with access limited to the intended audience and a verified download link. Do not make a private file public merely to satisfy a Site link. External storage has quotas too: check the current provider and account limits when size matters. An observed 256 MiB expanded-deployment limit in one project/tool is not a universal Sites account limit; check the actual host constraint rather than encoding that observation as policy.

Before publishing the page, verify that the external asset is the intended version, its recorded hash matches the downloadable bytes, the direct link works for the intended recipient, and the Site points to that exact link. Distinguish an accessible page from an accessible download. Keep existing downloads and libraries intact. Move an older download only when that migration is explicitly requested; first confirm the replacement bytes/hash and recipient access, then verify link readback and preserve the old URL or a working redirect. Do not delete or change unrelated Sites as part of download hosting.
