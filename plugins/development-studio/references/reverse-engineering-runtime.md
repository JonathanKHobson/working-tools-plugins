# Reverse-engineering runtime contract

Read before invoking a reverse-engineering provider for the first time in a task. This contract adapts the complete preserved REA workflow to the receiving host. Current user authorization and host requirements take precedence over examples in the imported guides.

## Ownership and readiness

Development Studio owns the portable `mcp.json` and compatibility `.mcp.json`, `scripts/rea_runtime.py`, the 207-tool fingerprint in `docs/rea-tool-catalog.json`, the workflows, validation and change tracking. The upstream MIT runtime and separately licensed engines remain attributed external dependencies. Do not install a second REA plugin or duplicate global MCP server. The full tool catalog is retained; registering a tool does not prove its optional engine is available.

The launcher reads only `~/.config/studio-tools/rea.json`. Its private binding supplies the exact 6.5.0 runtime root, Node executable and SHA-256, package entrypoint, integrity inventory path and SHA-256, analysis command catalog SHA-256, reviewed provider environment, and tool PATH directories. It verifies every installed package/dependency file and link, rejects added or changed files in `node_modules` and changed root package manifests, strips inherited environment variables, rejects unreviewed environment keys, requires a current-user-owned private nonsymlink temporary directory, and starts without an initial target. Provider binaries are trusted separately reviewed dependencies; PATH entries and engine directories are not made safe merely by hashing REA. The binding and engine acquisition receipts stay outside the public plugin. The trusted plugin code and private binding are outside the runtime inventory. Temporary output, empty directories and other runtime-root content are not integrity covered. Checks precede execution and cannot prevent a concurrent same-user modification. HOME is not inherited or overridden; engines can still resolve the user home through OS APIs. Environment filtering does not prevent filesystem credential access or guarantee secret isolation.

Use `python3 scripts/rea_runtime.py status` from the installed plugin root to verify readiness without starting a server. The plugin MCP invokes `python3 scripts/rea_runtime.py --mcp`. CLI analysis uses `python3 scripts/rea_runtime.py cli ANALYSIS-COMMAND ...`; setup, registration, doctor installers and updates are deliberately excluded from that entrypoint. It does not download anything at startup. If a binding is missing or changed, stop runtime invocation and use the reviewed setup procedure, rather than silently falling back to `npx`.

Before enabling the full MCP on Codex, configure the native plugin server `plugins."development-studio@personal".mcp_servers.rea` with `enabled=true`, `default_tools_approval_mode="writes"`, and per-tool `approval_mode="prompt"` for every name in `explicit_prompt_tools` in the catalog. Use the actual marketplace-qualified plugin ID on other hosts. Read back native effective configuration and live `tools/list`, comparing all names and schema fingerprint. These host settings are enforced by the client, not the JSON catalog or upstream annotations. Preserve stricter host policies; if the host cannot provide the required approval boundary, do not enable broad unattended MCP access. A client that auto-denies prompts may leave an operation unavailable until its supported approval flow is used. Do not bypass a denied call through CLI.

For an authorized acquisition, pin the official `morluto/rea` repository and `rea-agents` package, verify registry integrity/signatures/provenance and inspect dependencies before installing with lifecycle scripts disabled. Inspect optional native bindings and obtain pinned prebuilt assets from official publishers with verified digests. Never run an automatic fallback builder/downloader without review. A clean vulnerability result is not a malware certificate. Node must meet the release requirement; SQLite additionally requires Node 24.15+ in the 24.x line or 26+. Prefer a dedicated runtime over changing the system toolchain.

Use `binary_session` for live provider status, then a representative fixture for the capability needed. Ghidra can supply native decompilation; JADX/JDK Android analysis; WABT WebAssembly; built-in parsers package, JavaScript, managed metadata, Go/Rust and saved traffic; Frida supplies explicitly authorized instrumentation. Some Linux-only features and commercial providers cannot be made available on every host. Install useful nonredundant engines, not every interchangeable decompiler. Never label missing providers as security failures or claim the entire platform matrix was tested on one Mac.

## Static JavaScript lane

For an explicitly selected directory or ASAR, the reviewed command shape is:

```bash
python3 scripts/rea_runtime.py cli analyze-javascript-application "$TARGET_PATH" --json
```

Resolve the target from the current task and run from the installed plugin root. The target can be a copy in a task-owned directory. Use a bounded run with a dedicated temporary directory and minimal environment; avoid inheriting cloud/API credentials. Save potentially sensitive output only in the authorized project. REA parses target text, creates private temporary worker files and returns Evidence; it should not execute the analyzed application's source. It is not an OS sandbox. For hostile or especially sensitive artifacts, use an independently verified isolated analysis environment; do not claim isolation from a temporary working directory or clean environment alone.

A harmless first-use check uses a tiny owned fixture with an import/export relationship and a top-level failure sentinel. Require actual graph/Evidence output, intact input hashes and no target execution. Check the returned `error`, limitations and cleanup status, not only the shell exit code. This establishes only the tested static lane. Close task-owned processes and confirm temporary worker cleanup.

## Higher-impact operations

The full REA MCP exposes capabilities beyond static parsing, including process/debugger control, instrumentation, browser/Electron observation, filesystem outputs and device mutation. Before enabling a new MCP version or another provider, complete Master Security Toolkit's capability fingerprint and review actual command/version, tool schemas, target roots, network destinations, writes, credential/log behavior and the client's enforcement. Use the plugin-owned pinned launcher and native host approval policy. Preserve existing baseline servers. Never hide capability limits behind a broad success statement.

Live observation requires a named authorized target, explicit actions, data handling and cleanup. Do not set blanket auto-approval for debugger commands, Frida, browser/Electron scenarios, native UI actions or device changes. Remote endpoints require an explicit target and purpose; ordinary installation does not authorize connecting to arbitrary hosts. For untrusted samples use a separately verified isolated analysis environment. Browser work must use the host's supported browser-control rules. A user-owned app can still contain other people's confidential data. Do not browse profiles, capture sessions, bypass licensing or access controls, or install persistent helpers as a side effect of static analysis. These boundaries apply to the source guide examples as well as direct tool calls.

## Updates and rollback

No automatic updater or scheduler is part of this integration. Refresh only for a concrete need or an authorized maintenance task. Review the upstream diff, exact package and dependency lock, method/support changes and new tool surface. Stage the replacement beside the old runtime; rerun the relevant fixture and adverse cases, then change the private binding. Preserve the prior runtime and method snapshot until verification succeeds. Maintain source/output hashes and specific dispositions in the existing import record. Method changes use Development Studio's normal validator and native installation/parity workflow; do not edit installed caches.

Rollback restores the prior plugin files through the native plugin manager, disables only this plugin’s REA server through native configuration, and points the private binding back to the prior reviewed runtime. Preserve other plugin/server settings. Remove only the task-owned runtime after confirming no owned process is using it. Do not remove unrelated servers, global packages, engines or browser sessions.
