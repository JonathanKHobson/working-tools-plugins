# Compare module interfaces where change is difficult

Read for a requested module/interface design or architecture improvement where callers repeatedly coordinate the same rules, tests require knowledge of internals, or one change spreads across many files. Skip this review for routine fixes with a clear owner.

1. Bound the review to the user's named area. If none is named, use recent change history and concrete maintenance friction to select a small area. Read the project glossary and relevant decisions; retain its vocabulary. File count or thin wrappers alone do not establish a defect.
2. Describe the caller's complete contract: inputs, outputs, invariants, ordering, failure behavior, required configuration and relevant performance expectations. A useful module hides meaningful complexity behind a comprehensible interface. Apply the deletion test: if removing it would spread rules among callers, it may earn its place; if removal eliminates needless forwarding, simplification may help. Account for wrappers that enforce security, compatibility or an external protocol.
3. Trace the dependencies and choose tests suited to them. Pure in-process behavior can be exercised directly. A local stand-in can support fast integration tests, with its fidelity limits stated. An owned remote service may use a transport adapter; a third-party integration needs contract-aware fixtures or mocks plus appropriate authorized integration evidence. A fake's success is not proof of production compatibility.
4. Introduce a replaceable interface when real variation or a concrete testing/integration need justifies it. Keep private seams private. Do not add ports solely for a hypothetical future adapter or insist that every module use one shape.
5. If the choice is consequential, compare at least two materially different designs, such as a small operation-oriented interface and an interface optimized for the common caller. Each comparison includes caller example, hidden complexity, dependency/testing approach and tradeoffs. Delegate independent alternatives only when useful and authorized; no fixed worker quota.
6. Recommend the smallest change supported by evidence. Name affected files, preserved behavior, expected reduction in caller knowledge or scattered change, and the check that could disprove the benefit. If it conflicts with an accepted decision, state the new evidence before proposing to reopen it. An analysis request ends with this recommendation; implement only within the task's authorization.
7. For an authorized refactor, test observable behavior through the public interface and preserve contract coverage. Map old tests to retained coverage before removing only redundant tests; retain distinct boundary, integration and failure cases. A test that changes during a refactor is not automatically worthless. Verify callers and affected behavior after integration.

Completion: the recommendation identifies observed friction, alternatives and tradeoffs; an implemented change additionally has behavior and coverage evidence. Use a small diagram only if it helps comparison. No report CDN, browser helper, package installation or automatic glossary rewrite is required.
