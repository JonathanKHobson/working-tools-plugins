# Build web software

This method owns the task contract and delivery checks. The complete framework procedures stay in official Build Web Apps. Use [the provider map](../../references/platform-providers.md) to resolve its actual installed skill paths; do not copy commands from stale cache paths or claim the provider’s tool connection comes from this package.

1. Identify the current framework, package manager, existing design anchors and task flow. Record 3–8 source anchors before visual claims: ID, source viewport, region, node/selector, observed fact and intended change. Preserve accepted components and states unless a redesign was requested.
2. Select only relevant full Build Web Apps methods: frontend-app-builder for a new visual application/redesign; frontend-testing-debugging for existing UI defects; react-best-practices for React/Next performance; shadcn-best-practices for that component system; supabase-best-practices for Postgres; stripe-best-practices for payment flows.
3. Implement a complete path including loading, empty, error and recovery states where affected. Validate data and secrets at the server boundary. Use the existing auth/payment provider in its intended test environment; do not fabricate backend success.
4. Run the project’s checks, then inspect the actual rendered flow at the same reference viewport and the affected narrow/keyboard states. Use the currently supported browser provider. Keep a bounded task-owned server/session record and close it at handoff unless intentionally continuing.
5. Verify changed anchors and real persistence/integration behavior. A local preview is local evidence; confirm the deployed URL separately only when deployment is requested.

If the official provider or browser capability is unavailable, continue source implementation and appropriate local checks. Identify the exact missing runtime evidence. Do not replace the provider with a one-paragraph approximation or silently install accounts/dependencies.
