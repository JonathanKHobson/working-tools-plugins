# Course production guide

## Asset states
Use planned → drafted → reviewed → revised → approved for specified destination → packaged → uploaded → launch-tested → released. Record actual states, not the whole chain as a mandatory workflow. Approval must name the artifact/version and destination. An old approval does not authorize new private content.

## Production register
Asset ID; objective; source version; format; learner task; dependencies; author; reviewer; rights/access; status; verification evidence. Keep source files distinct from rendered exports and deployment packages.

## Dated Coursera pattern
Kyle's 2024 GP Development workbook used an outline and task-1 review, scripts/slides/key takeaways review, recording review, course-shell setup, and beta-testing checklist. It inspected whether the learner environment matched the recording, files opened, captions were accessible/accurate, task titles matched objectives, and quiz feedback explained answers or directed review.

These are useful production concerns, but the old workbook's title lengths, number of objectives/options, timing, and platform instructions must be rechecked against a current supplied template. Its “launch” checkbox was false in the archival workbook even though the correct live course showed Launched in September 2026.

## Recording brief
Task outcome; learner starting state; source/version; visible actions; spoken explanation; expected result; error recovery; files; captions/transcript; stop point. Record a representative task, check intelligibility and screen readability, and fix the pattern before recording all tasks. Clear speech matters; do not require a “perfect accent” from the historical vendor checklist.

## Software drift
Prefer task labels and success states over brittle coordinates. Check current UI, entitlement, region, and login needs. If a current feature differs, update the affected step and sample outputs. Keep an offline or screenshot-based fallback for learning when live access is not essential.

## LMS handoff
State the exact requested package specification and target environment. Verify file integrity, import, launch, scoring, completion, resume, links, and accessible interaction where applicable. Preserve evidence of a tested learner role rather than only an author preview. Do not claim an HTML export is SCORM or that a ZIP file is LMS-compatible without the corresponding packaging and launch checks.

## Maintenance
Name an owner, likely drift triggers, and the assets affected. Review after material product/policy changes or observed learner failures. Reconsider whether the original need and destination task remain relevant; retire or replace obsolete instruction instead of updating assets indefinitely. Do not create recurring automations unless requested.

## Operational readiness
Reuse dependency rows from analysis: required condition → proposed/accepted owner → due point → readiness evidence → fallback. Confirm facilitator preparation, learner prerequisites, usable procedures, required access, and opportunities to practice where relevant. An asset register does not replace those checks. Do not invent agreement, access, or a completed rehearsal.

## Optional tool routes
Use available document, presentation, video, or LMS tooling only when the output needs it. The `edu-role-play` skill includes a separately gated runtime lane. Do not require any external connector merely to author a course or handoff note.
