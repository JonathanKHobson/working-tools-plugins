# Reviewed full method adaptation

This method retains the useful source production sequence. The following contract overrides every inherited provider or scope assumption: current host tools and user instructions have precedence; use available browser/connectors for a supplied URL, and read an identified local file when authorized. Do not search unrelated private files to infer an ambiguous target. No affiliate offer, tracking link, nondisclosure instruction or vendor comparison prohibition applies. Existing Graphic, UX, Video and Data owners coordinate adjacent work. All final visible deliverables require rendered inspection and applicable design review; file generation and geometry checks alone do not prove appearance or import behavior. Never assert file dimensions, optimization or conversion without measuring the delivered file.

## Goal

Create a usable static SVG that represents the supplied process, structure or sequence accurately, with readable labels and relationships. The diagram's purpose determines whether it emphasizes movement, reporting, approval, milestones or exploration. A diagram on a client-facing page can be read as a commitment; distinguish confirmed operations from proposed structure, estimates and unresolved facts.

## Instructions

### 1. Get what actually happens

Use the user's description, identified document, existing diagram or screenshot. Inspect a supplied URL or local path through current authorized tools. Establish what an ambiguous reference names before drawing; never infer operations from unrelated files.

A business name alone does not establish its process. Infer routine visual decisions from context, then ask only for a missing fact that materially changes the content or deliverable. Respect supplied colors, layout, orientation, names and notation. Include real people, roles and systems only when source-supported and appropriate to the sharing context.

If the user asks for an illustrative example, provide a clearly labeled proposed or generic model. Mark unknown operational details without inventing a business, role, deadline, fee or approval gate. A proposed model must remain visibly distinct from a diagram of actual operations.

### 2. Pick the diagram type and a starting layout

Choose by the question and supplied structure. The following counts are starting guidelines for a compact diagram, subordinate to semantic completeness, user requirements and legibility. They are not geometric limits. Use additional rows, a larger suitable canvas, grouped detail or linked diagrams when the structure warrants it; do not remove actual nodes or relationships merely to meet a cap.

| Diagram | Relationship to represent | When to use it | Starting layout guideline |
|---|---|---|---|
| Process flow | An action or state change and what moves next; name the actor when known and relevant | A sequence such as onboarding or service delivery | About 5-9 steps and a few decisions; preserve all actual endpoints |
| Swimlane | Action and owner, with cross-lane connectors identifying handoffs | Responsibility and waiting between parties | About 2-4 lanes and 6-12 steps, adjusted to the actual roles and sequence |
| Decision tree | Condition and its supported outcomes | Qualification, triage or option selection | A few levels per view; binary, multiway or open-ended outcomes as supported |
| Org chart | Reporting, approval, collaboration or accountability, labeled or distinguished by notation | Who reports to whom or who decides what | About three levels or a dozen roles per compact view; use supplied roles or names |
| Timeline | An event or milestone and its supported date, duration or order | Historical sequence, plans or engagement phases | About 4-7 milestones per row; distinguish actual, proposed, estimated and committed dates |
| Quadrant / 2×2 | Positions relative to explicit axes and evidence or stated judgment | Prioritization, positioning or comparison | Two axes with clear poles and a readable set of items; meaningful quadrant labels where useful |
| Journey map | The experience, actions and relevant service response at each stage | A client or user experience | About 4-6 stages per view; include friction or drop-offs when source-supported |

Preserve every actual outcome relevant to the selected scope. A decision may have two outcomes, several outcomes or an unresolved outcome. If only one branch is shown intentionally, label it as a partial view or filtered path; do not add an invented failure branch. When a source implies an unresolved path, mark that uncertainty explicitly.

For a Gantt, use the existing [Gantt and schedules owner](../../gantt-and-schedules/SKILL.md). Use the existing node-link/layout procedure selected by Structural Diagrams for a legitimate mind map or relationship map. A mind map can represent exploratory associations; it need not become a process flow. A funnel requires supported counts if it makes numerical claims. A RACI can be a responsibility matrix rather than an org chart.

State the chosen type and major visual assumptions briefly when they help the user inspect the result.

### 3. Write the content and relationships before drawing

For a process flow, create a numbered content model before placing boxes. Where the source provides an actor, use an action-oriented line:

```
{known actor or system} {does what to what} → {what moves, or the relevant condition}
```

If the actor is unknown or irrelevant to the diagram's purpose, preserve the known action or state and mark responsibility unresolved only when needed. Do not force every event, milestone or concept to become an action by a person. For another diagram type, use its appropriate model: reporting relationships, condition/outcome paths, dated events, concept links or journey stages.

- Trace each substantive node and relationship to supplied content or a clearly marked proposal. Decorative grouping and legend elements explain the model and must not introduce facts.
- Prefer concise action labels for process steps. Retain the meaning when shortening; record material changes to source wording.
- Label connectors where their meaning would otherwise be ambiguous. A conventional reporting line or chronological connection may be clear from its notation and legend; it does not require a repetitive label on every edge.
- Include all supported decision outcomes within scope. Flag genuinely missing paths without assuming they are binary or must represent failure.

A useful process test is to read the connectors separately: can a viewer understand what moves, what triggers a transition and where uncertainty remains? Also read the nodes alone to check that actions or states retain their meaning.

**Illustrative wording example, not a model of the user's firm:**

```
1. Client submits the intake form          → completed form
2. [role] reviews the stated criteria      → accepted, declined, or more information needed
3. Accepted: [role] prepares the agreement → agreement ready for review
4. Declined: [response]                    → [next step]
5. More information needed: [request]      → additional information
```

The branches are present because this example states three outcomes. A source with different outcomes gets different branches. Do not transfer these steps, roles or criteria into a real firm's diagram without evidence.

Prefer clear actions over vague phrases such as “review occurs” when accountability matters. Passive voice or state labels can be appropriate when the actor is unknown, the subject is an automated system or the diagram emphasizes an event rather than responsibility. Preserve that distinction rather than inventing an actor.

When a diagram becomes crowded, first improve layout, grouping and label wording. Merge steps only when their meaning, owner and trigger genuinely allow it. Keep detailed content in a linked subdiagram or accompanying description when that suits the reader's task, and make the scope visible. Do not conceal missing steps in a legend. A legend may explain multiple relationship types, status cues or placeholder notation.

Return the content model or a concise wiring list when it makes revision easier. Routine diagrams do not require a separate approval checkpoint before rendering.

### 4. Separate facts, proposals and unresolved details

Do not silently add operational specifics. Use supplied or verified evidence for real roles, people, systems, dates, fees, thresholds and gates. A historical timeline records what happened; a proposed timeline describes a plan; a committed delivery timeline states obligations. Label those statuses rather than treating every milestone as a promise.

| Missing detail relevant to the diagram | Possible short placeholder |
|---|---|
| Responsibility | `[role]`, `[owner]` |
| Duration or service commitment | `[turnaround]`, `[duration]` |
| Fee, retainer or rate | `[fee]`, `[retainer]`, `[rate]` |
| Decision threshold | `[threshold]` |
| System | `[system]` |
| Person's identity | `[name]` |
| Date or milestone | `[date]`, `[milestone]` |
| Count, rate or percentage | `[count]`, `[%]` |
| Source-implied unresolved outcome | `[outcome]` |

Only introduce a placeholder when the detail is required by the stated structure or question. Unknown actors, failure paths and compliance gates are not mandatory additions. If a proposed model needs one, mark it as proposed and explain the assumption.

Keep placeholders short enough to fit their shapes, with the full verification question in the fill-in list. Use a visible cue such as a dashed border plus a clear legend to distinguish unresolved content. The cue helps review; it cannot prevent accidental publication. Do not rely on color alone to show status.

### 5. Fix the palette and the rules every element obeys

Choose a palette for the intended background and maintain consistent color roles: ink, ground, primary, muted connectors/placeholders and an accent for exceptions when useful. Reuse supplied brand colors where readable; fewer colors may suffice. State the chosen palette when it helps the user reproduce the artifact.

**Brand color safely, as arithmetic and not judgment.** Compute WCAG relative luminance:

```python
def lum(hexstr):
    def ch(c):
        c = c / 255
        return c / 12.92 if c <= 0.03928 else ((c + 0.055) / 1.055) ** 2.4
    r, g, b = (int(hexstr[i:i+2], 16) for i in (1, 3, 5))
    return 0.2126*ch(r) + 0.7152*ch(g) + 0.0722*ch(b)

def ratio(a, b):
    la, lb = sorted((lum(a), lum(b)))
    return (lb + 0.05) / (la + 0.05)
```

- **Label directly on a saturated brand fill:** use it only if it clears **4.5:1** against white or
  against the ink. If it clears neither, demote the brand color to the border and fill with a tint.
- **The 12% tint:** `c_tint = round(c * 0.12 + 255 * 0.88)`. A 12% tint of essentially any hue
  holds well over 14:1 against a near-black ink. This is the safe default for any text-bearing node.
- **A light brand color cannot be a border.** `#F59E0B` is 2.15:1 on white and `#FACC15` is 1.53:1
 : both fail the 3:1 non-text minimum, so a raw amber border is a ghost. Darken by multiplying
  every channel by *k*, stepping *k* down from 1.00 in 0.01, until the ratio clears 3:1.

**The one silent failure, and the whole reason step 5 exists:**

> **SVG `<text>` does not wrap, does not clip, and raises no error. An over-long label draws
> straight out of its box and over the next node.** There is no autofit to blame and no warning at
> build time. The file opens: it just has two labels on top of each other.

**So measure every label before you place it.** Use this embedded advance-width table (Adobe AFM,
units per 1000 em, ASCII 32-126). Helvetica and Arial are metrically identical to each other, so
one pair of tables covers both:

```python
REG = [278,278,355,556,556,889,667,191,333,333,389,584,278,333,278,278,556,556,556,556,556,556,
556,556,556,556,278,278,584,584,584,556,1015,667,667,722,722,667,611,778,722,278,500,667,556,833,
722,778,667,778,722,667,611,722,667,944,667,667,611,278,278,278,469,556,333,556,556,500,556,556,
278,556,556,222,222,500,222,833,556,556,556,556,333,500,278,556,500,722,500,500,500,334,260,334,584]
BLD = [278,333,474,556,556,889,722,238,333,333,389,584,278,333,278,278,556,556,556,556,556,556,
556,556,556,556,333,333,584,584,584,611,975,722,722,722,722,667,611,778,722,278,556,722,611,833,
722,778,667,778,722,667,611,722,667,944,667,667,611,333,278,333,584,556,333,556,611,556,611,556,
333,611,611,278,278,556,278,889,611,611,611,611,389,556,333,611,556,778,556,556,500,389,280,389,584]

def afm(s, px, bold=False):
    t = BLD if bold else REG
    return sum(t[ord(c)-32] if 32 <= ord(c) <= 126 else 556 for c in s) * px / 1000.0

def fit(s, px, bold=False):
    return afm(s, px, bold) * 1.03 + 4      # initial fit allowance; calibrate against the actual rendered font
```

**The table and budget are source modeling heuristics, not a rendering guarantee.** The source recipe adds `×1.03` plus four units as an initial allowance. This pass has not reproduced its original font measurements. Calibrate fit against the actual renderer and font; use measured glyph widths for accented text and non-Latin scripts rather than assuming the ASCII table covers them.

For this AFM-based starting variant, use a compatible font stack and inspect actual text fit:

```
font-family="Helvetica, Arial, 'Liberation Sans', sans-serif"
```

A fallback or a different font can change glyph widths. Recompute shape sizes when the font changes.

**Sizing a node:**

```
W1 = max(120, ceil4(fit(label) + 28))              # 28 = 14 units of padding each side
if W1 <= 220:            one line,  box = W1 × 48
else:                    split the label at the word break that MINIMISES THE WIDER LINE,
                         then W2 = max(120, ceil4(max(fit(a), fit(b)) + 28))
    if W2 <= 220:        two lines, box = W2 × 72
    elif one unbreakable word and fit + 28 <= 240:  one line at that width
    else:                shorten without losing meaning, or enlarge/reflow the node and recompute fit
```

Balanced splitting is the layout mechanism, not a fallback: greedy first-fit produces a wide line
plus an orphan, which makes the box *wider*. *"Send contract for signature"* is 230 units on one
line and 134 split as `Send contract` / `for signature`. Reject a split that leaves under three
characters or a lone article or preposition on a line; move the break one word earlier.

For the compact node variant, start with labels around 32 characters and one or two lines. Shorten without losing essential meaning, or enlarge the shape and adjust the layout. Longer labels and additional lines are legitimate when they remain readable at the target size. Record material shortening and retain the complete wording in the content model.

The geometry below is a concrete starting recipe for a compact, portable SVG. Adjust its canvas, margins, type, shape sizes and routing for the actual structure and receiving surface. Recompute checks after changing the recipe; readability and semantic completeness govern.

| Property | Starting recipe |
|---|---|
| Root element | `<svg xmlns="http://www.w3.org/2000/svg" width viewBox height>`: **all four**, matching 1:1. Without `xmlns` it is not a standalone SVG and renders blank |
| Canvas | Start at width 1200; size height to content and margins. A square quadrant may start at 1000×1000. Use another size or aspect ratio when the target surface or structure requires it; inspect whitespace at the displayed scale |
| Margin | 48 on all four sides: 32 of it a routing lane for a branch running back up |
| Type scale | Start with 16/700 node labels and 16/400 edge labels/legend. The supplied AFM tables model only regular and bold; measure other weights with the actual font |
| Node box | Width per the sizing rule, 120-220 (240 for one unbreakable word). Height 48 one line, 72 two lines. Padding 14 horizontal, 12 vertical |
| Corner radius | `rx="8"` process · `rx="24"` terminal (a stadium) · `rx="6"` org-chart box |
| Text baseline | **Compute it.** One line: `y = cy + 0.35 × fontSize`. Two lines: first baseline `y = cy − 4`, tspans at `dy="0"` then `dy="20"`: **and re-state `x` on the second tspan**, or line 2 starts where line 1 ended and runs out of the box |
| Strokes | Node border 2, edge 2, `stroke-linecap="round"`. A 2-unit stroke is centred on the path, so a 220-wide box occupies 222: count it in every gutter and margin check |
| Gutters | Rank 64 horizontal, 56 vertical. Sibling 32 (24 absolute minimum) |
| Edge routing | Orthogonal segments are a simple portable starting choice. Curved routes are valid when they improve the diagram; align arrowheads to the actual path tangent and inspect overlaps |
| Edge anchors | The centre of a box edge, never a corner. *n* edges off one side sit at `W/(n+1)` intervals |
| Arrowheads | An explicit filled `<path>`, length 12 and half-width 5, with the line ending 1 unit *inside* the head so anti-aliasing leaves no notch. **Never `<marker>`** |
| Edge labels | 16/400 muted, offset 10 perpendicular. On the line, put an opaque knockout `rect` behind it in the ground color, `rx="4"` |
| Decision diamond | `W = 1.20 × (fit + 28)`, `H = 96`, **label ≤ 16 characters**: a diamond narrows toward its points, which is *why* decision labels must be short. Prefer a distinctly filled `rx="8"` rect unless classic notation is asked for |
| Placeholders | `stroke-dasharray="6 4"` in the muted color |
| Contrast | Label on its fill **≥ 4.5:1**, target 7:1. **Every stroke, border, and arrowhead ≥ 3:1 against the ground**: this is the one people skip, and a 2:1 border is the difference between a diagram and a ghost |
| Background | An **opaque, full-bleed, square-cornered `<rect>`** in the ground color, drawn first. Never rounded: rounding leaves four transparent corners that go black on a dark page |
| Coordinates | Integers, snapped to a 4-unit sub-grid |
| File size | Under 100 KB. Over 250 KB means an embedded raster, which must never be there |

Around 12 nodes is a useful review point for a compact flowchart, not a hard limit. Check crossings, traceability and text at the intended display size. Increase or restructure the view when that preserves the supplied content and remains legible; split only when separate views help the reader.

**Portability: match the receiving application.** For a simple SVG intended for varied importers, prefer: the basic shapes, `<path>`
with absolute commands, presentation attributes on every element, `<text>` and `<tspan>`, `<g
transform="translate(…)">`, `<title>` and `<desc>` as the first two children, `role="img"` and
`aria-label` on the root, and 6-digit hex colors. The following alternatives reduce compatibility risk for this variant. They are not universal SVG prohibitions; use other features when the target supports them and verify an actual reopen/import before claiming compatibility:

| Feature to check or avoid in this portable variant | Compatibility risk | Simple alternative |
|---|---|---|
| `<foreignObject>` | Renders in a browser tab only. Figma, PowerPoint, Illustrator and every rasterizer drop it: you get an empty rectangle, and it looks fine to you | `<text>` + `<tspan>`, sized by the fit budget |
| CSS in `<style>`, and `class=` | Importers flatten or drop selectors, and an SVG inlined into a page leaks its `<style>` into the page's CSS with no scoping | Presentation attributes on every element |
| `textLength` / `lengthAdjust` | Where honoured it stretches the glyphs, so a mis-measured label ships **distorted** rather than visibly wrong | Size the box to the text, never the text to the box |
| Web fonts, `@font-face` | An SVG loaded in an `<img>` is a no-network sandbox. The font never loads and the layout reflows on the reader's machine | The closed stack above |
| `dominant-baseline` | The classic silent failure: honoured in modern browsers, ignored by older Safari and every importer. The text still renders, just 8 units low, and nobody notices until publish | Compute the baseline |
| `<marker>`, `<use>`, `<symbol>`, `xlink:href` | Dropped or flattened inconsistently on import | Repeat the geometry: these files are tiny |
| Filters, gradients, shadows, `clipPath`, `mask` | The things importers most often drop or mis-scale | Flat fills and 2-unit borders |
| `<script>`, SMIL `<animate>`, `:hover` | Never runs in an `<img>`, and an upload may sanitize it | Nothing. A diagram is static |
| 8-digit hex, `rgb()`, `hsl()` | Not valid SVG 1.1; dropped by older parsers | 6-digit hex: pre-compute the blended solid |
| `em`, `rem`, `%` units | No font-size context to resolve against inside an `<img>` | Unitless user-space numbers, including on the background rect |
| A raw `&`, `<` or `>` inside `<text>` | **The fastest way to make an unopenable file.** *"Review & approve"* unescaped makes the whole document unparseable and the user sees a blank | `&amp;`, `&lt;`, `&gt;` |

**Dark backgrounds:** an opaque ground is a simple way to keep a static file's contrast independent of the page behind it. If dark placement is required, prepare and test the needed variant; a starting palette is ground `#0F172A`, surfaces `#1E293B`, ink `#F8FAFC` and edges `#94A3B8`, with verified brand-accent contrast. Responsive color behavior depends on embedding and renderer support. Claim a file adapts only after testing both receiving contexts; otherwise provide clearly named light/dark assets when needed.

### 6. Build the SVG, name it, validate it, and deliver it

**The stem.** Slugify the business, client, or subject: lowercase, runs of non-alphanumerics to a
single hyphen, trimmed: `Bend & Flow` → `bend-and-flow`. With no subject, use `diagram`. Name the
file **`{stem}-{diagram-type}.svg`**: `bend-and-flow-onboarding-flowchart.svg`. Never a bare
`diagram.svg`, `flowchart.svg`, or `output.svg`: fixed names collide across conversations and
overwrite a file an earlier chat is still pointing at. If the name exists and you did not write it
in this conversation, append `-2`, then `-3`.

**Validate before you claim the file exists.** All of this is standard library:

```python
import xml.dom.minidom
xml.dom.minidom.parse(path)          # if it does not parse, it is a text blob with an .svg name
```

and for every node assert, in code:

```
fit(label, fontSize, bold) + 2 * horizontalPadding <= boxWidth
boxX >= margin and boxX + boxWidth + strokeWidth <= canvasW - margin
boxY >= margin and boxY + boxHeight + strokeWidth <= canvasH - margin
fontSize * displayedWidth / canvasW >= chosenReadableTextFloor
```

If an assertion fails, **fix it and re-validate.** Never hand over a file you know does not parse
or has a label outside its box.

**The ladder. Stop at the first rung that works, and name the rung you landed on in one line.**

1. **Write the `.svg`** and validate it as above. This is the deliverable.
2. **Render and inspect a preview.** Use an existing available renderer without starting unnecessary browsers or servers. The following historical ladder is conditional, not a requirement to try every provider. Try `rsvg-convert`, then `cairosvg`, then
   `inkscape --export-type=png`, then headless Chrome (`--headless --disable-gpu
   --screenshot=out.png --window-size={W},{H} file.svg`), then macOS `qlmanage -t -s 1200 -o .`.
   One attempt each, no retries, no stack traces. **If one works, look at it and say what you
   checked**: a render catches an overlap the assertions missed. If none works, preserve the SVG draft and say plainly that rendered QA remains incomplete; do not sign off its visual quality.

   ⚠ **`qlmanage` offsets and crops an SVG instead of honouring its `viewBox`.** A node near the
   right or bottom edge can look missing in a `qlmanage` thumbnail while the file is perfectly
   correct. Prefer Chrome and size the window to the canvas. **Never "fix" a diagram on
   `qlmanage` evidence alone**: re-render somewhere faithful before you change a single
   coordinate, or you will chase a bug that is not in the file.
3. **If the file cannot be written** (read-only filesystem, sandbox): output the complete SVG in
   one fenced ` ```svg ` block and give the filename to save it as. **SVG is text, so the block is
   the file**: this is a full deliverable, not a degraded one, and say so.
4. **If the SVG would be truncated by message length:** cut the diagram to its top level, ship
   that **complete**, and list what you dropped so they can ask for a second diagram. **Never ship
   a truncated SVG**: a cut-off SVG is an unopenable file, strictly worse than a smaller correct
   one.
5. **Floor:** the wiring as a numbered list, labelled as the structure and not as a diagram file.

**Never end a turn without one of the five. A description of a diagram is not a diagram.**

**Hand over the alt text.** The root `<title>` and `<desc>` are good practice, but a diagram placed
as an `<img>` exposes only the alt attribute to a screen reader: so give the user a ready-to-paste
alt line in the reply. Do not claim the file is self-describing.

### 7. Handle change requests

**A change request rewires; it does not redraw.** Same wiring, same palette, same stem, and
overwrite the file you wrote in **this** conversation.

- Adding a step updates the content model and its supported relationships; a decision includes the actual outcomes relevant to scope.
- Filling a bracket moves that line from bracketed to stated, and updates every element repeating it.
- Reflowing to fit preserves substantive content and relationship meanings; merge handoffs only when the source supports it.
- A different process uses a **new stem** rather than overwriting another artifact.


## Delivery boundary

Show the actual artifact and its usable file path, the chosen style or palette, source-based content, missing facts, alt text, measured output properties and rendered QA evidence. Preserve originals and create a named revision when needed by the project. Do not claim a preview, import, compression or public release that was not verified.
