# Evidence-grounded profiles, empathy maps and journeys

Use when the requested deliverable is a persona, task profile, empathy map or journey map built from authorized research. Research Toolkit owns the evidence and can produce the complete textual artifact directly. UX Design Toolkit can review or render it when requested; its absence does not prevent this method. This is an independently authored Research procedure, not execution of a publisher method.

## Establish the decision and source record

1. Name the decision, task, population/context and artifact requested. A small task-specific profile can be more honest than a broad demographic persona. Do not produce several fictional people simply to fill a template.
2. Inventory the supplied interviews, observations, logs, survey responses and existing findings. For each used item retain source ID, participant/case identifier, date/context when known, precise excerpt or event locator, collection method and relevant permission. Keep personally identifying details in the authorized private research record; use pseudonyms where appropriate.
3. Mark each artifact statement as observed behavior, participant statement, analyst interpretation, hypothesis or unknown. Quotes require exact supplied wording and attribution. A paraphrase is labeled and still carries its source. Silence is not evidence of a belief or emotion.
4. Review source coverage before grouping cases. Count actual participants/cases rather than excerpts when discussing recurrence. Note contradictory cases, missing perspectives, setting differences and how recruitment limits transfer. A cluster of quotations from one participant does not establish a representative segment.

## Construct a persona or task profile

Choose the pattern that affects the decision: a shared task, constraint, strategy or context. State the membership rationale and supporting cases. With one case or thin evidence, produce a bounded case/task profile and label generalization as untested. Do not invent age, identity, employment, accessibility needs or technical confidence for visual plausibility.

Build the profile around the user's objective and actual behavior: task and context; goal; current approach; material constraints; supported needs; pain points; evidence and countercases; design/research implications; unresolved questions. Keep a named job-to-be-done tied to the task and situation instead of assigning motives from a demographic stereotype. A proposed implication carries the finding that motivates it and the smallest evaluation that could change it.

Useful output fields:

| Field | Required treatment |
| --- | --- |
| Profile title and scope | Describe the evidenced task/context; do not imply representativeness beyond coverage |
| Goal and approach | Source-backed behavior or stated goal, with IDs |
| Constraint or need | Evidence and affected step; unknown stays unknown |
| Pain point | Event, quote or documented friction; separate severity judgment |
| Interpretation | Rationale, plausible alternative and confidence limitation |
| Implication | Proposed change/test tied to a finding; not a measured improvement |
| Coverage and gaps | Cases, settings, contradictions and missing evidence |

## Construct an empathy map

Separate what a participant said and did from proposed thoughts and feelings. Populate the first two with actual quoted statements or observed actions. Populate an emotion with self-report when available; distinguish a researcher's inference and give its alternative explanation. Do not fill every quadrant if evidence is absent.

For each entry record content, evidence status, source and setting. Conflicting statements can remain side by side when time or context explains them; do not smooth away a tension to create a neat personality. Conclude with the consequential question the map leaves open and how it could be investigated, rather than treating an inferred feeling as proof of product impact.

## Construct a journey map

1. Set the scenario's start/end, actor/context and actual sequence. Reconstruct the path from observed events and participant accounts. Mark recalled timing or sequence uncertainty; do not add a funnel stage because a generic template contains it.
2. For each supported stage record trigger, goal, actions, touchpoints, system/organizational response, obstacle, evidence and relevant consequence. Separate participant-reported thought/feeling from analyst interpretation. Unknown values remain empty or explicitly unknown.
3. Include backstage dependencies only when the source establishes them, such as a staff handoff, approval or data refresh. Label a proposed dependency to investigate; do not invent an operational cause from visible frustration.
4. Compare material case variants: a first visit, return, failed attempt or recovery when actually in scope. Keep exceptions and abandoned paths visible. A successful path does not establish that an error state works.
5. Prioritize opportunities using evidenced task cost, consequence, coverage and confidence. Keep the recommended intervention separate from the observation. Define a realistic check for the change and the result that would weaken the recommendation.

A textual journey table can use stage, trigger/goal, observed action, response/touchpoint, reported thought/feeling, obstacle, source/status, opportunity and next test. Adapt columns to the reader's decision; source/status must remain recoverable even if a graphic uses fewer columns.

## Verify and deliver

Trace every consequential field to a source or a clearly labeled hypothesis. Recheck counts, quotations, sequence, contribution and privacy. Make sure recommendations do not claim measured benefit or a representative population. Return the complete requested artifact with its scope, evidence trail, contradictions and smallest open questions. Do not substitute a handoff summary when source material permits the artifact itself.

When evidence is too thin for the requested generalization, still produce the bounded supported profile/map and state the limit. Ask only for evidence necessary to resolve a consequential missing field. For a requested graphic or Figma board, send the complete fact/status contract to the existing design owner and preserve labels through layout; a saved visual is a separate production state.

## Constructed example and check

Synthetic source E1: participant P1, observed return after one week, opened the model tab and searched for the active scenario. Synthetic source E2: P1 said, “I cannot tell which scenario I last used.” No emotion or timing measurement was recorded.

Profile: returning scenario-model user, based on one case; goal is to recover the prior scenario. Approach/constraint: searched model details because current scenario was not identified in the supplied view [E1]. Stated uncertainty: could not identify the last-used scenario [E2]. Emotional state: unknown. Generalization to all users: untested.

Journey stage: return to model. Trigger: resume prior work [E1]. Action: search model tab [E1]. Thought/report: uncertainty about last scenario [E2]. Backstage cause: unknown. Proposed opportunity: test a visible scenario/history cue. Next check: compare an actual return task with/without the cue, preserving formula correctness; fewer searches or accurate scenario identification must be observed before reporting improvement.

If a second source reports a different return strategy, retain it as a variant rather than forcing a common persona. If a requested empathy map contains no feeling evidence, leave that area unknown. The example is fictional method support, never a participant finding for a live project.
