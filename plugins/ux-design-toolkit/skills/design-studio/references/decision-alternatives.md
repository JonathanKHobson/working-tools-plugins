# UX decision alternatives and task perspectives

Use when a material interaction/design choice has plausible alternatives or the user asks for a UX panel, contrasting perspectives or simulated task walkthrough. Keep one user outcome and the bounded surface. Routine fixes with adequate evidence need one focused review.

## Shared method and evidence boundary

Resolve the installed `work-management:worker-delegation` owner and read its `references/decision-council.md` when contrasting perspectives or independent work helps. It owns quick/explore/compare/council selection and evidence-based synthesis. Without that owner, use a single-pass perspective review labeled as such. A single assistant playing several roles is not an independent council.

Use quick for the main uncertainty, explore for distinct directions, compare for existing options on common criteria, and council only for a consequential decision that merits independent review. Do not equate a majority, agreement score or persona count with usability evidence. Design Studio retains final integration; UXHC retains rubric, severity and report validation; Research Methodology retains real study planning.

## Explore and compare options

1. Identify the user's task, observed anchors, approved content/system and constraints. Separate observations, supplied participant data, assumptions and proposed changes.
2. Produce two or three materially distinct alternatives when the choice is unresolved. Include the current approach if viable. Tie each to the same task; do not generate aesthetic variants that leave the decision unchanged.
3. Compare recognition, task effort, feedback/recovery, accessibility risks, implementation cost and reversibility only where relevant. Cite observed anchors and existing evidence. State what would make an option fail or change the recommendation.
4. Select a provisional direction using task/evidence fit and constraints. Preserve unresolved objections. An implementation request authorizes the bounded change and rendered verification; a concept/review request stops at that stage.

## Simulated task perspectives

Use constrained task contexts, such as first visit, returning after interruption, keyboard-only input, or limited bandwidth. These are analyst-generated hypotheses, not representative personas or real participants. Do not invent demographic knowledge, lived experience, participant quotations, completion rates or emotional outcomes.

For each useful perspective, state the supplied/assumed context, task path, observed affordance, predicted friction and a check that could falsify the prediction. Exercise the actual path when authorized and available. An analyst's successful walkthrough verifies that interaction in those conditions; it does not establish real-user usability. Record unexercised states as unverified.

If actual workers review independently, give them the same evidence and brief, with distinct bounded assignments. Withhold others' conclusions during their first pass; then compare source-grounded disagreements. If the same assistant generated all perspectives, label the result `single-assistant simulated task perspectives`.

## Critique before integration

Challenge the most consequential, severe, thinly supported or expensive-to-fix findings. Restate the claim neutrally, consider an alternative explanation, check audience assumptions and identify evidence that could raise or lower severity. For formal heuristic findings, use [UXHC evaluator bias guard](../../ux-heuristic-compass/references/evaluator-bias-guard.md) and its existing `stress_test_heuristic_finding` tool when callable. For a broader source/argument claim, use the existing Critical Compass owner only when it is relevant and available; do not duplicate MCP wiring.

A diagnostic response suggests questions; it does not independently observe the interface or validate the fix. Re-inspect the relevant anchor/task, then retain, qualify, revise or discard the finding with a reason. Preserve dissent that affects the decision. Do not downgrade a finding merely because another lens prefers the design.

## Deliver

Return the chosen/provisional option, evidence basis, strongest remaining objection and a concrete verification or real-research need. Keep hypotheses and observed checks separate. If participant evidence is required, hand the question to [research inputs](research-inputs.md) rather than reporting simulation as research.
