# Product and web surfaces

Identify the visitor's job on this surface: decide, operate, read, or experience the work. Use that job to set hierarchy and density. A checkout or editor should make the next task obvious; a portfolio should let the work lead; a document should support scanning and sustained reading. The product category does not automatically determine the layout.

Choose this intent per route or section. A marketing home page and its account workspace need different composition and motion even when they share a brand. For a working surface, prioritize familiar controls and stable task context; entry animation must not delay action. For a reading surface, prioritize sustained readability and navigation through the material.

Inspect the existing brand, code, components, tokens, routes, real content, and sibling screens. For a new page, library or feature in the same product, read the closest related source and view its rendered screen before arranging the new surface. Note the reusable page order, type scale and minimum, color roles, corners, cards, controls, search/filter and header behavior; keep task-specific differences explicit. Reuse the actual component and style implementation where feasible. Prefer the established system for a narrow fix. For a new or requested redesign, choose a deliberate composition: one focal point, clear grouping, readable type measure, spacing rhythm, restrained color roles, and an image or artifact that helps the user understand the offer or task. Avoid filler metrics, decorative controls, and repeated cards when they add no information. Use a concise local design direction; generate visual concepts only when they materially clarify the decision.

Missing design documentation does not mean a missing design system: shipping components and repeated decisions can establish the current visual authority. Distinguish repairing or extending that system from an authorized replacement. Do not create a parallel token set or redesign sibling screens merely because an external style guide prefers another look.

For app UI, keep behavior consistent across screens. The same operation should use the same label, feedback, state model, and navigation result unless the workflow has a real reason to differ. Check default, hover, focus, selected, disabled, busy, empty, loading, error, and success states where applicable. Forms need persistent labels, helpful errors, clear required/optional signals, and protection against duplicate submission. Tables and search need meaningful no-results and partial-error states; asynchronous results should not overwrite a newer query. Keep important navigation and recovery paths available at narrow widths, high zoom, and with long content.

Treat accessibility as part of the user path. Use semantic controls, visible focus, logical order, sufficient contrast, non-color state cues, accessible names, reduced-motion behavior, and predictable focus after overlays or errors. Visual inspection alone cannot establish assistive-technology compatibility; exercise the relevant interaction with available tools and report the limit.

For dialogs, load the current frontend accessibility guidance and check the actual component contract: accessible name and modal semantics, keyboard entry, appropriate focus containment, intended Escape/close behavior, and focus return. Do not substitute a screenshot or generic keyboard checklist for that interaction test.

Implementation follows the owning repository's framework and conventions. Reuse matching components and assets; do not convert a simple site into a new stack for visual convenience. A maintained design system can justify a concise design context file or behavioral contract; a one-off page or small fix does not. Verify the built page in a real renderer and test the affected path before declaring it complete.

For a theme/system change or recurring contrast failures, use [system craft checks](system-craft.md). A local fix needs only the affected pairs and components, not a new design-system document.

Before arranging a new or revised surface, inventory the real content, claims, limitations and actions. Choose containers around that inventory; never fill a template slot by inventing evidence or compressing away a material qualification. For generic composition or a change from browsing to comparison, use [context-sensitive design review](../../design-review/references/intentional-design.md). Preserve stable interaction conventions while changing structure only where the task warrants it.

## Interactive design decisions

When a requested site or redesign leaves material audience, purpose, brand or visual-direction choices unresolved, first inspect current project evidence and approved decisions. Infer reversible details; use a concise question or an interactive comparison when the answer would materially change the result. Do not require a form when the brief is already sufficient. UX Design owns this decision support; Sites owns the actual site construction and hosting. Preserve the single Shareables-site default for a shareable request.

For a decision rather than open exploration, curate a small set of meaningfully different alternatives first—often two to four, not a fixed quota. Explain the tradeoffs and recommend a direction. Offer revision or rejection and avoid presenting a large gallery when expert narrowing is the useful work. A diagram or annotated process can also make a consequential question understandable before collecting the answer.

For Kyle, prefer a useful visual decision surface for spatial or many-option choices: representative directions with their audience fit and tradeoffs; a searchable template gallery; or a small intake containing audience, primary action, brand constraints and chosen reference. Reuse the existing Design Library gallery for template selection before creating another picker. Support a freeform answer and “use your recommendation”; do not force a preset that misses the brief. A short ordinary question is still appropriate when a panel adds no clarity.

Choose the feedback mechanism deliberately:

- **Presentation:** previews, annotated comparisons or a proposed design direction communicate an approach. Browsing, hovering and viewing do not approve it.
- **Shared state:** a supporting MCP App can expose selected state to the assistant, but only through its documented host bridge. Verify that state actually arrives; local component state is not automatically assistant-visible.
- **Explicit handoff:** prefer a clear “Use this direction” or “Send choices to chat” action for committing inputs. Return the selected IDs, revision, meaningful options and freeform brief; acknowledge what was received before using it. Test one real end-to-end handoff. Never label a local click as sent before host acknowledgment.

If a preview has no working host bridge, offer a copyable brief or saved result plus the ordinary chat question. Explain that it is a local preview; do not make the user infer whether a choice reached the assistant. Handle edits, stale selections, pending, error/retry and keyboard access. Only selected task-relevant inputs belong in the handoff; do not stream unrelated private content. A design selection is not authorization to publish, spend, send to others or change account access.

Use source screenshots, embeds where supported, or generated image concepts as visual reference targets when they resolve ambiguity in composition, tone or imagery. Preserve approved brand and source anchors. Label generated concepts as illustrative, not functioning UI or tested product evidence. Pair each direction with a short explanation of what to keep/change and the intended user outcome; avoid spending generation effort on decorative variants that do not change a decision. Use the installed image-generation skill for requested generation and Graphic Design for asset production; validate the implemented site separately. Record the selected direction in the owning project brief, with source/provenance and user-confirmed versus proposed state, rather than treating a transient preview as durable approval.
