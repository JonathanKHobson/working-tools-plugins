# Verification and handoff

Match the checks to the change. A copy edit needs readback in the actual surface. A product interaction needs a user path. A visual redesign needs source-to-rendered comparison. A poster needs inspection of its final export. Do not run a broad test campaign for a narrow reversible change, but do complete required repository checks and any test that resolves a concrete risk.

Before visual signoff, compare the 3–8 named anchors from the source or baseline with the latest rendered artifact. For a new or changed sibling surface, place prior and new rendered captures side by side at the same viewport and theme, with matching states where possible. Check hierarchy, type size, color roles, edges, shared controls and interaction cues against the mapped conventions; correct unintended drift before signoff. Record the viewport, page, state, and each intentional deviation. Inspect a full view for hierarchy, then focused regions for text, imagery, controls, and spacing that cannot be judged at overview scale. Check one narrow view when the artifact is responsive. After a correction, recapture the affected anchor and confirm the defect is gone. If the related rendered source is unavailable, label the continuity check unverified rather than claiming a match.

For interactive surfaces, exercise the changed path with realistic data. Confirm the visible response to an action; check keyboard path and focus for controls; examine loading, empty, error, disabled, and success states that the change touches. A successful build or saved revision proves only that stage. Source inspection may identify likely behavior but cannot prove the rendered journey. Formal accessibility testing requires its own method and should not be claimed from screenshots.

For an entry or join flow, keep a compact evidence trace from an unseeded direct link: what appeared during a delayed load, the primary action shown before joining, the response while it was pending, the authoritative success/failure result, and what remained after reload or return. Include whether another prominent call to action competed with the intended path. If a state could not be produced, mark it unverified; do not describe a static screenshot, tool availability, or a planned heuristic scan as an executed journey review.

After the functional check, make one task-only newcomer walkthrough without relying on implementation knowledge. At each observed state ask: What can I do now? How will I know it worked? How do I recover or leave? Note where the interface itself does not answer. Label this a cognitive walkthrough, not a user test or participant finding. If the review missed a problem, inspect the actual prompt, evidence and route used before attributing the miss to prompt length or knowledge overload; those are hypotheses until supported.

For a concrete entry-state example, see [workshop invitation](interaction-resilience.md#worked-example-workshop-invitation).

For exports and external apps, inspect the receiver artifact. A design uploaded as an unused asset is not placed. A frame visible in Figma may still be a raster image. A link that exists may not be publicly available. A file generated by an editor may not be the file sent to print. Use precise stage language and verify the stage the user requested.

Make a bounded pass: inspect, fix material issues, then confirm changed anchors. Stop when the requested result is sound; record remaining limits such as untested devices, unavailable accounts, printer proof, or unexercised live data. The final handoff leads with the delivered artifact and links it, then states what was checked and any material limitation.

## Current web accessibility checks

For web work, choose the checks relevant to the affected path and verify the current criterion rather than turning a remembered number into a universal rule. WCAG 2.2 AA target size is generally 24 by 24 CSS pixels with defined exceptions such as spacing and inline text; larger targets may still be better for the audience. This is distinct from an arbitrary all-controls 44-pixel rule. See [W3C target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html).

Check reflow at a width equivalent to 320 CSS pixels for vertically scrolling content, retaining necessary two-dimensional exceptions such as meaningful tables/maps. Test keyboard focus against sticky headers, banners and overlays so the focused control is not entirely hidden by authored content. See [W3C reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html) and [focus not obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html). These targeted checks do not establish whole-product conformance.
