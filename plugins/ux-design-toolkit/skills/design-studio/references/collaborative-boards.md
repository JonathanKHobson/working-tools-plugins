# Collaborative board hierarchy

Use for a shared whiteboard's layout or review. This is interface judgment; Workshop Facilitation owns the session process, Instructional Design owns learning objectives, and the current Figma provider owns editor authoring and functional checks. Reuse the actual brief and source board, not a generic gallery. Read the [human-systems decision guidance](human-systems-decisions.md) when making workload or memory claims.

## Make the current job recognizable

Separate a short orientation/route, current work, and indexed reference. Give the current question the strongest emphasis, place instructions beside its response area, and state completion and next use. Use literal stage names even if a small playful cue adds warmth. One current assignment is a design recommendation for facilitated work, not a fixed limit on visible information.

Distinguish staged disclosure of future tasks from progressive disclosure of optional detail. Keep constraints, authority, and criteria available early; keep interdependent alternatives and evidence together at comparison time. Hiding more is not automatically better. If people must repeatedly leave to retrieve the same fact, co-locate the relevant excerpt or summary with a link to its original.

Do not expose a full question bank, every activity variant, and all method instructions as simultaneous assignments. Preserve the source material in an indexed reference path; retain exact wording and IDs, mark shortened text as summary, and keep contradictory evidence findable. When adapting a populated board, record Change / Keep / Defer against the actual authorized scope. A cleaner view must not erase contributions, minority concerns, or historical decisions.

## Give working objects equal and readable treatment

Use native editable inputs and meaningful labels. Apply a shallow reading order: task → context → prompt → work → completion → navigation. Let spacing, grouping, and a restrained type hierarchy distinguish these roles. Semantic colors need text labels; an attractive overview is not proof of contrast or access.

Compare alternatives under the same headings and similar visual emphasis. Show reasons and Unknowns, not just colored scores. Avoid allowing a larger or more polished card to imply endorsement. Keep evidence → candidate → decision → action traceable; proposed, shortlisted, decided, and accepted are distinct states.

Size from real content. Reflow, expand, or link secondary detail when an extra distinct idea or long response arrives. Do not shrink essential text to fit a fixed room grid. Prefer a small purposeful arrival interaction with Pass and a text/scribe/non-drag route; visual polish should not add mandatory drawing, audio, or precision games.

## Review the actual working experience

Use 3–8 observed anchors, including opening/current task, contribution, evidence, comparison, and decision/actions where relevant. Record actual editor viewport, chrome/panels, and zoom. Inspect a small laptop view (around 1366×768) and a larger view (around 1440×900) when available. These are useful test conditions, not validated universal thresholds. Canvas font values and a distant overview cannot pass readability.

Check whether the user can find the current question, input location, completion cue, Home, and evidence without scanning the whole board. Record actual behavior if a participant attempts this; a reviewer prediction is an inference. Inspect wrapping and overflow using realistic content and an additional contribution. Keep comparable options visible together at a working scale, not only in a tiny fit-all screenshot.

Verify functional behavior through the provider: response editing, real links, reveal/restoration, background-only locking, keyboard/non-drag contribution, and roles/follow/voting when used. Hidden content is presentation state, not privacy. A drawn button is not a working control; a link does not prove automatic reveal; local viewport motion does not prove multiplayer following. Label each relevant result `verified/pass`, `failed`, `not tested`, or `not available` with evidence. Supply a synchronized text route; screen-reader support requires its own actual browser/role/assistive-technology check.

Preserve a usable review state after the session: completed work visible, decision summary prominent, unresolved items indexed. A reset applies only to an unused master or authorized copy. Template marketing, generated objects, structural checks, visual QA, functional rehearsal, participant usability, and workshop outcomes are separate evidence states.

## Research and adoption limits

Adapted from the supplied FigJam Collaboration Research Handoff (2026-10-03), particularly its research synthesis, board specification, template review, and acceptance tests. The motivating report described a board with too many visible activities and source questions; it is a reported usability problem, not a measured general cognitive limit. No board was operated or user tested for this plugin update.

[NN/g's progressive disclosure guidance](https://www.nngroup.com/articles/progressive-disclosure/) distinguishes optional detail from staged steps and cautions against separating interdependent tasks; independently rechecked during adoption. [MacNeil et al., Freeform Templates](https://arxiv.org/abs/2305.00937) studies classroom template/freeform use. The supplied full-paper review identifies Miro, not a controlled FigJam trial; this update rechecked the abstract only. The study is a reason to allow adaptation, not proof of a particular room count or reduced overwhelm.

The package's geometry, card budgets, palette, timing, and suggested orientation targets remain proposed design defaults. Adopt mechanisms selectively; do not import its whole gallery, fixed sequence, or screenshots. No third-party code/assets or template imports were adopted. Current board behavior, account access, and accessibility require separate live evidence.
