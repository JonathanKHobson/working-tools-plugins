# Rive state binding and asset handoff

Read when integrating or changing an interactive `.riv` asset, especially data binding, named states, events or a React host. Apply [vector playback](designer-authored-vector-playback.md) for loading, accessible alternatives, reduced motion and teardown. This procedure adds the asset-to-application contract; it does not install a runtime or author a `.riv` file through an unavailable editor.

## Establish the contract

Inspect the actual exported asset and installed runtime before choosing APIs. Record the asset revision, artboard, state machine, view model and instance names when present (or legacy input names/types), renderer/package/version, external font/image/audio dependencies and authoring source. When any name or property is missing, report that mismatch and retain a usable fallback instead of silently selecting another animation.

For each property or trigger, write a row containing its exact name, type, allowed range or enum, initial value, direction of flow, owning app state, and reset behavior. Decide which values come from the application and which are presentation-only. A success pose must follow confirmed success; it cannot complete a pending operation. Avoid two-way feedback loops by defining a single authoritative owner and ignoring unchanged echoed values. Multiple cards should have separate view model instances unless shared state is intentional.

Check the installed package's API against the primary documentation. Current Web documentation marks `stateMachines`, direct state-machine inputs and Rive Events as deprecated, with `stateMachine` replacing the plural parameter in v2.41.0. Prefer supported data binding for new work; preserve compatible legacy integrations until a scoped migration is tested. Do not apply the Web version number or signatures to Flutter, native or React packages without verification. See [Web parameters](https://rive.app/docs/runtimes/web/rive-parameters) and [data binding](https://rive.app/docs/runtimes/web/data-binding).

## Bind deliberately

1. Load the chosen file and resolve the intended artboard and state machine. Select the binding branch supported by both asset and runtime: a data-binding asset resolves its view model; an existing legacy asset may have no view model and instead uses named state-machine inputs. Preserve that supported legacy input/trigger path without inventing view model names or requiring an asset migration. Record migration as separate work when needed. For the data-binding branch, resolve the intended view model. Verify property names and types before subscribing or assigning. Use automatic binding only when the exported defaults match the agreed contract; otherwise explicitly select and bind the intended instance using the installed version's API.
2. Set meaningful initial values before the first visible interactive frame where supported. Keep a poster or noninteractive loading state until ready, avoiding a flash of a success/default value. In current React documentation, `onRiveReady` receives the loaded instance and supports pre-render binding; data-binding hooks resolve after the first frame. Check availability in the installed React package before using it. Older integrations may need a ready-state effect and concealed loading frame. [React contract](https://rive.app/docs/runtimes/react/parameters-and-return-values).
3. Subscribe once to the selected view model instance, or connect the validated legacy input handles for the legacy branch. Validate incoming values, bound numeric ranges, and reset transient triggers on the documented lifecycle. After replacing the asset or view model, detach subscriptions from the old instance and revalidate the new contract. Do not retain handles into a released instance.
4. Treat asset-triggered events as input. Map known events to explicit app actions; never turn an arbitrary event string into navigation, code execution or a network request. In a legacy event integration, explicitly set automatic URL handling to false where supported. Map the known event to an application-owned fixed destination or independently checked allowlist; never trust a URL merely because it arrived in a recognized event. Reject arbitrary external URL payloads and respect user gesture requirements. Current Rive guidance prefers data binding for new work. [Legacy events](https://rive.app/docs/runtimes/web/rive-events).
5. Define who releases each resource. The React wrapper manages its owned runtime according to its package contract; application subscriptions and observers still need cleanup. In a directly owned high-level Web instance, use its documented `cleanup()` when finished. A paused render loop is not disposal. A low-level integration must cancel its own loop and release the objects it created in safe dependency order; do not manually free objects still owned by another wrapper.

For WASM delivery, use a version matching the runtime and the project's approved asset policy. Record required CDN fetches or self-hosted resources, including fonts; do not assume an offline `.riv` also makes its dependencies offline. Check renderer feature support before selecting a smaller runtime. Editor scripting is a separate authoring capability: obtain the editable source, verify protocol/runtime support and test in the real editor before claiming scripting works.

## Acceptance and handoff

Exercise two independent instances, a legacy asset without a view model, missing property/type mismatch, an asset event carrying an unapproved external URL, initial loading, real success/failure, rapid updates, reset, asset replacement, live reduced-motion preference, keyboard fallback, hidden/resumed page and repeated mount/unmount. Check that stale callbacks cannot update the new asset, app values remain authoritative, and events cause only intended actions. Inspect actual pixels and accessible controls. Deliver the contract, source/asset revisions, package/version, fallback and observed results. Without an asset/runtime these remain implementation instructions, not a verified Rive integration.
