# Choose a motion technique from behavior

Use after choosing a purpose and pattern in [web adaptation](motion-pattern-web-adaptation.md). This is original guidance checked against primary platform/library documentation on 2026-10-05, prompted by a user-supplied research summary. No third-party skill, code sample, package or installer is incorporated. Verify target-browser support and the project's installed API version before implementation.

## Start with the control contract

| Need | First option to assess | Escalate when |
| --- | --- | --- |
| Small deterministic entrance, emphasis or state change | Existing CSS transitions/keyframes; explicit animated properties | Playback orchestration needs cancellation, reversal or seeking: consider WAAPI or the existing animation library |
| Gesture following with velocity continuity | Existing physics/spring implementation | Use an actual spring model when velocity and retargeting matter; a sampled easing curve alone does not preserve live velocity |
| Item moves between layouts | Existing layout system, FLIP or supported View Transitions | FLIP measures first/last geometry, applies an inverse transform and animates to identity; batch reads/writes and remeasure after layout changes |
| SVG line draw, path travel or morph | SVG/CSS/WAAPI where suitable; existing GSAP methods when already selected | Complex shape normalization or orchestration justifies additional tooling only after a concrete gap is demonstrated |
| Illustrated vector playback | Existing designer-authored-vector-playback reference | Choose the actual player by feature support; a format specification does not supply a renderer |
| Large decorative particle field | Small SVG/DOM prototype or an existing canvas renderer | Profile actual device/frame cost before changing renderer; there is no universal 200-node boundary |

CSS and WAAPI can support interruptible behavior; interruptibility does not require a spring. Define whether cancellation freezes, reverses or settles to the latest semantic state. Avoid stacking stale completion callbacks after rapid input. [WAAPI](https://developer.mozilla.org/en-US/docs/Web/API/Web_Animations_API) provides playback controls. [Motion's animation documentation](https://motion.dev/docs/animate) distinguishes physics-based springs with velocity from duration/bounce-based variants. CSS [linear()](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/easing-function/linear) can approximate a predetermined spring-shaped progression; it is not itself a live physics simulation.

## Pattern implementation decisions

- **01, 03, 06, 11 — shared identity:** preserve semantic DOM and real state while animating a visual relationship. [View Transitions](https://developer.mozilla.org/en-US/docs/Web/API/View_Transition_API) animates snapshots, not a replacement interactive workspace. Feature-detect, use unique matching names for participants, preserve a direct update fallback, and test interrupted navigation, focus and reduced motion. Same-document and cross-document support/requirements must be checked separately.
- **02, 04, 07 — lists, tabs, stacks:** stagger only when it clarifies order; users should not wait for every row to animate before acting. Use stable keys, settle to the latest selection and keep inactive content out of keyboard traversal. Native transitions may suffice; an automatic layout animator is optional and still needs interruption and content-height checks.
- **05 — chart morph:** preserve values and valid encoding first. Native interpolation of SVG path data requires the same number, types and order of commands, not merely equal point counts ([SVG 2 path data](https://www.w3.org/TR/SVG2/paths.html#TheDProperty)). Rectangles do not automatically become a valid line path. Normalize corresponding geometry deliberately or crossfade valid charts; inspect intermediate values and topology. Specialized morph tooling is an option, not a mandatory GSAP dependency.
- **08 — dock:** derive a bounded visual scale from distance to stable target centers. Coalesce pointer updates with animation frames and avoid measuring/reflowing on every write. Time-based smoothing should behave consistently across refresh rates; a fixed per-frame interpolation factor can vary in perceived speed. Preserve keyboard/touch alternatives.
- **09, 12 — masks and reveals:** identify which layer is clipped. On the image, moving from `inset(0)` toward a fully collapsed clip conceals it; reveal by expanding the visible region. On an overlay, retracting that overlay uncovers the image. Keep masks decorative and the underlying content accessible. Check [clip-path semantics](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/clip-path), final crop and browser support instead of blindly applying a 0-to-100 recipe.
- **10 — type:** verify font axes and ranges using [font-variation-settings](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/font-variation-settings). Width/weight changes may alter layout or paint. Reserve space, preserve a semantic heading, check font-load failure and profile before scaling to many glyphs. Embed/subset fonts only when rights and the deliverable warrant it.
- **13 — perspective:** agree on the flat hierarchy before applying depth. Bound rotation and depth, check clipping/stacking and avoid making scroll/pointer motion a prerequisite for reading. Smooth-scroll replacement is a separate product decision, not a required motion layer.
- **14 — focus band:** default to readable emphasis for real tables. Blur-plus-mask compositing is an optional illustrative technique, not a verified reconstruction of the screenshot. A sharp window requires the underlying content and mask geometry to remain aligned; inspect contrast and render cost before adoption. Never hide factual alternatives to drive a selection.
- **15 — paths:** stroke dash offset can draw or move a dash pattern; moving a dot along a path is a different operation. Select CSS motion paths, SVG animateMotion or existing path tooling by required control. SVG/SMIL supports [event-based starts](https://developer.mozilla.org/en-US/docs/Web/SVG/Reference/Attribute/begin); “SMIL cannot be interactive” is false. Complex app-state integration may still be clearer in the existing JS controller. Verify pause, reset and reduced motion on the actual implementation.
- **16 — particles:** cap work based on measurement, reuse geometry and stop owned work when offscreen/unmounted. Canvas can reduce DOM overhead but does not automatically outperform SVG, and still needs a semantic/static counterpart.

## Budgets are testable choices

### Additional implementation checks from Part 2

- **GSAP availability:** the [3.13 release](https://gsap.com/blog/3-13/) makes the former bonus plugins available through the public package at no charge, including commercial projects. [MorphSVG](https://gsap.com/docs/v3/Plugins/MorphSVGPlugin/) can normalize differing path structures; native path interpolation's restrictions do not describe that plugin's capabilities. Inspect its mapping and intermediate geometry rather than assuming normalization preserves chart meaning. Follow the [GSAP adapter](gsap-methods.md) and current license; free pricing does not mean unrestricted licensing.
- **FLIP scheduling:** double `requestAnimationFrame` is one possible way to separate style commits, not an essential part of every FLIP implementation. The [original FLIP explanation](https://aerotwist.com/blog/flip-your-animations/) includes both frame-separated CSS and explicit WAAPI keyframes. Measure first/last layouts at deliberate boundaries, then choose scheduling that actually commits the inverse state in the target framework. Test fonts, reparenting and interruption. A library implementation is an option, not the definition of production readiness.
- **3D continuity:** `transform-style` is not inherited; set `preserve-3d` on the relevant non-leaf containers that must retain a shared depth context, not every ancestor in the whole document. Specific [grouping values](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/transform-style) flatten descendants: examples include opacity below 1, a non-none filter or clip-path, and overflow other than visible or clip. Merely declaring opacity 1 or overflow visible does not flatten the context. Inspect the actual ancestor/value chain.
- **SVG delivery context:** a self-contained declarative SVG animation may run as an image, but image embedding is not equivalent to inline SVG. [SVG image restrictions](https://developer.mozilla.org/en-US/docs/Web/SVG/Guides/SVG_as_an_image) include disabled scripts and restrictions on external resources. An outer page cannot treat the image's internal nodes as inline DOM controls. For interactive scrubbing or reliable pause/reset, choose an embedding/controller that exposes the required control and verify it in that context.
- **Blur and masks:** check the [backdrop-filter compatibility table](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/backdrop-filter) against supported browser versions. A prefixed declaration may serve older targets; do not claim all Safari versions require it. A registered custom property permits interpolation only when its syntax and values support it; it does not establish compositor acceleration.
- **Reduced motion:** show the equivalent usable state, not blindly the animation's last keyframe. A closed dialog should remain closed until opened; search loading must not become fake results; a paused process must not appear complete. Disable unnecessary spatial movement while keeping truthful state and feedback.

No recipe guarantees 60fps from its property names. Transform/opacity can still incur expensive surfaces or main-thread work; clip-path and offset-distance are not universally compositor-only. Treat 200 path points, 200 particles, a 600ms stagger ceiling and device-pixel-ratio 2 as trial budgets, not verified platform limits. Evaluate complexity, viewport, blur, renderer, device and frame timing before selecting a threshold. A Canvas pixel-sampling recipe also needs an origin-clean image and a fallback when pixel reads are unavailable; do not promise success for arbitrary remote logos.

Prefer transform/opacity for spatial movement and fading, but do not prohibit necessary path, mask, color or font animation. Avoid repeated layout-triggering writes and read/write interleaving. Profile rendering cost rather than claiming all transform animation is free. [web.dev's performance guide](https://web.dev/articles/animations-guide) explains the tradeoff; layer promotion also has costs. Use explicit property lists instead of `transition: all` so later style changes do not acquire unintended motion.

There is no universal under-300ms requirement. Choose response speed, travel distance, reading hold and settle time for the task; a functional control should respond promptly even if a decorative tail continues. A one-file HTML artifact and eight-second loop are useful only when requested for a standalone motion study/feed piece. Production sites retain their architecture and user-driven states.

Frequency check: does this effect help on the tenth exposure? Limit replay of delight that distracts from recurring work. Apply reduced motion and inspect its actual equivalent state. For automatically starting movement lasting more than five seconds alongside other content, provide pause/stop/hide unless essential; see the exact conditions in [WCAG 2.2.2](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html). This is not the complete accessibility checklist, and reduced motion alone does not fulfill every playback-control requirement.

## Smallest useful verification

Try the selected effect in one real component. Verify its main action, rapid retargeting, resize, reduced motion, asset failure and teardown; inspect playback at delivery size and profile representative load if performance is in question. Record tested browser/device and observed failures. Static skill review verifies instructions, not runtime behavior. Do not install a research candidate just to make the tool list longer.
