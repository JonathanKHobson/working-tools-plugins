# Conditional Emil motion methods

Use this adapter for a bounded web UI motion build, opportunity review, motion critique, or terminology question when the incumbent motion guidance does not answer the specific choice. The complete pinned MIT source is in [`libraries/emil-motion-methods`](../../../libraries/emil-motion-methods/PROVENANCE.md). Read the complete task-matching method and its support before acting; this adapter only explains how it fits the maintained UX workflow.

| Task | Complete source to read | Distinct contribution |
| --- | --- | --- |
| Implement one UI transition or gesture | [`animate/SKILL.md`](../../../libraries/emil-motion-methods/source/skills/animate/SKILL.md) and the matching section of [`animate/RECIPES.md`](../../../libraries/emil-motion-methods/source/skills/animate/RECIPES.md) | Frequency and purpose gate; trigger-aware origin, explicit entrance/exit, press, tooltip, toast, drag and hold-to-confirm examples. |
| Find useful motion in an existing screen | [`find-animation-opportunities/SKILL.md`](../../../libraries/emil-motion-methods/source/skills/find-animation-opportunities/SKILL.md) | Inspect feedback, teleporting state, spatial continuity, groups and gestures; record rejected candidates as well as proposals. |
| Critique implemented motion | [`review-animations/SKILL.md`](../../../libraries/emil-motion-methods/source/skills/review-animations/SKILL.md) and [`review-animations/STANDARDS.md`](../../../libraries/emil-motion-methods/source/skills/review-animations/STANDARDS.md) | Assess purpose, frequency, origin, interruption, timing, reduced motion and perceived feel against actual playback. |
| Name an unfamiliar motion effect | [`animation-vocabulary/SKILL.md`](../../../libraries/emil-motion-methods/source/skills/animation-vocabulary/SKILL.md) | Disambiguate the observed effect before choosing implementation; the glossary is vocabulary, not a design mandate. |

The useful sequence for an implementation is: identify the action and how often it is used; name the motion's purpose; check whether animation helps the task; preserve existing tokens and component semantics; choose the least complex technique that meets state, interruption and performance needs; implement the source recipe where it fits; then inspect playback, keyboard/touch behavior, focus and reduced motion in the actual product. A visual review should include the origin, midpoint, settled state, repeated trigger and interruption. For gestures, test pointer capture, a second touch, boundary resistance and velocity on a real target device when applicable. For an opportunity audit, cite current screen/code evidence and explicitly record at least one rejected candidate when the surface offers one.

Treat Emil's numerical curves, duration ranges, spring settings, `scale(0)` and high-frequency thresholds as candidate defaults to test against this product, not universal gates. The source itself allows exceptions (for example, a 400 ms toast and 500 ms drawer beside its 300 ms rule). Its absolute `transform`/`opacity`-only rule and Motion shorthand acceleration claim require profiling and current library/version verification. Existing [motion technique selection](motion-technique-selection.md) remains the implementation authority for CSS, WAAPI, View Transitions, springs, layout work and browser compatibility. Preserve actual accessibility needs even if a source recipe shows a gentler fade under reduced motion; some users need motion removed entirely. Do not add a dependency merely for a fade or replace an existing accessible component with a hand-built shell.

The source's greeting-only response, fixed report format, permission language, and instructions to write code or decline a broader request do not override the current user task. No source script or runtime was admitted. UX owns live interaction state, focus and reduced motion; Graphic Design owns visual direction across time; Video Production owns rendered scenes, narration and export. Cite or retain the MIT notice when copying source text or code into a deliverable.
