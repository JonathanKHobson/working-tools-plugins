# Design systems

When orientation helps, briefly name this skill’s outcome, needed input and expected result, then proceed. Broader help uses the [plugin introduction](../../README.md); skip maintainer notes unless needed.


Inventory, document, extract or evolve reusable UI tokens and components while preserving a coherent design system.

When creating, substantially updating or packaging a reusable design template, maintain a source-grounded `DESIGN.md` and link it from its template `SKILL.md`. Read [portable template specifications](references/template-design-contract.md) when creating, updating or packaging that foundation. Include only useful supporting files, preserve native measurements and verify the delivered reference closure. That contract also separates reader/content decisions from structure/style, provides a filled cross-medium example, and specifies positive/failing review cases. Reuse its compact section when the current template needs a content contract; keep components tied to information and behavior.

For a new or comprehensive UI kit, an existing-kit gap audit, or a reusable component handoff, read [the UI-kit method](references/ui-kit-method.md) first, then only its task-relevant references. It connects coverage, measurements, behavior, art, adoption and evidence. Ordinary small fixes keep their existing scope and do not require the whole method.

The UI-kit method owns that end-to-end route. Select an inherited source playbook below when its particular extraction, typography, color or layout operation adds needed depth; once selected, read it completely with the maintained host boundaries.

## Workflow

1. Identify whether the task is a new kit, system capture, extraction, audit or evolution; inspect existing code and related rendered screens before defining tokens or components. Reuse the incumbent system unless the user explicitly requests a new direction; mark unavailable prior designs as an evidence gap.
2. Read the UI-kit method for a kit task, or the complete selected playbook for its particular operation; follow the relevant inventory, naming, token/component and migration rules.
3. Compare changed consumers and states. Document deliberate exceptions and unresolved drift without repairing unrelated parts.

## Deliver and verify

Deliver usable tokens/components or system documentation and the checked adoption points.

## Example boundary

Good: extract repeated spacing into an existing token family with consumer checks. Bad: replace an approved palette during a documentation task.

Use the owned native adapter in the runtime guide for detector/live/hook commands; do not execute an upstream downloader or silently register a second hook. The brief and verified incumbent design govern style. For edits, load the complete craft-floor playbook. Preserve function/content and perform bounded rendered checks of changed anchors.
