# Shareables Design-System Contrast, Color, And Spacing Feedback

Status: planning note
Created: 2026-05-15
Source evidence: SVG visual-language gate rejection, recurring Shareables visual QA observations, and `design-system/research/svg-visual-language-gate/bad codex_examples/codex-feedback.md`.
Positive benchmark: `design-system/research/svg-visual-language-gate/good_examples/quality-bar-warm-editorial.html`.

## Summary

The rejected SVG sample gallery exposed a broader Shareables design-system issue: agents can satisfy technical validation while still producing weak visual output. The recurring failures are not limited to SVGs. They show up across Shareables themes, templates, style sources, generated visuals, and local review artifacts whenever color, contrast, spacing, alignment, and semantic use of tokens are underspecified.

This note should inform the next general design-system hardening slice before expanding more templates, widgets, icons, or visual assets.

## Positive Reference Pattern

Claude's Warm Editorial quality bar shows what the design system should ask agents to do before generating visual assets:

- Name the concept first.
- Lock the palette before drawing.
- Make every shape serve a structural, semantic, or ornamental role.
- Prove key geometry instead of guessing plausible coordinates.
- Decide what drops out at 24px and 32px.
- Review rendered output before calling a sample successful.

This is not only an SVG rule. The same pattern applies to templates, cards, charts, callouts, dark themes, badges, thumbnails, and other Shareables visuals.

## Recurring Failure Pattern

- Colors are used as decoration instead of semantic tokens.
- Contrast is assumed from theme intent instead of checked per rendered pair.
- Dark themes drift into low-contrast navy-on-black or incoherent accent use.
- Accent colors appear without a role, especially red/pink/orange marks in warning, decision, and decorative contexts.
- Style sources can feel like recolors of the same layout rather than distinct design systems.
- Utility visuals become generic icon-library output instead of a deliberate Shareables language.
- Spacing and alignment issues pass code-level checks but fail visual review.
- Generated visual systems lack hard shape, palette, contrast, and size budgets.
- Human review findings are too easy to trap inside one artifact lane instead of feeding the general design system.

## General Design-System Rules To Add

1. Every style source needs a contrast-paired token matrix.
   - Define text-on-paper, text-on-surface, muted-on-paper, accent-on-paper, accent-on-surface, button text, caution text, risk text, and focus ring pairs.
   - Record whether each pair is suitable for normal text, large text, non-text UI, or decorative use only.

2. Every style source needs semantic color roles.
   - `primary`, `accent`, `positive`, `caution`, `risk`, `critical`, `muted`, `border`, `focus`, and `surface`.
   - Decorative use should not borrow risk/warning colors.
   - Warning/caution colors should not appear as accidental pink/red unless the role calls for it.

3. Dark themes require separate approval.
   - Dark palettes should not be generated by inverting a light style.
   - Require a human-approved dark background, surface, text, muted text, border, accent, and status palette.
   - Require visual proof for cards, charts, callouts, tables, icons, and CTAs before promotion.

4. Spacing needs visual budgets, not only CSS tokens.
   - Define minimum comfort insets for page shells, cards, callouts, tabs, tables, and dense review galleries.
   - Add alignment checks for repeated cards, icon frames, badges, and thumbnail grids.
   - Treat cramped vertical rhythm as a style-source failure, not a content-only issue.

5. Generated visuals need hard budgets.
   - Palette budget: no unapproved colors.
   - Shape budget: avoid path noise and accidental ornament.
   - Contrast budget: meaningful marks must pass normal text or non-text contrast expectations depending on role.
   - Size budget: icons and motifs must work at the actual rendered size.

6. Review evidence must feed back into shared style-source docs.
   - A failed artifact should update the relevant style-source notes, not only its local review packet.
   - Repeated failures should become QA warnings or registry requirements.

## Backlog Recommendations

- Add a style-source contrast token audit for all current style sources.
- Add a `validate_style_source_contrast` helper or equivalent QA rule before new style-source promotion.
- Add semantic color usage warnings for accidental risk/caution colors.
- Add dark-theme promotion gates before treating Dark Analytics as a normal default option.
- Add spacing/alignment visual QA fixtures for repeated cards, icon grids, callouts, tables, and hero/section transitions.
- Add a human-feedback intake field to review packets so recurring visual mistakes can promote into general design-system hardening work.

## Acceptance Criteria For A Future Hardening Slice

- Every style source has a documented contrast matrix.
- Every style source has semantic color roles with allowed use cases.
- Dark Analytics is either repaired with proof or remains experimental/paused.
- Render QA or style QA can warn on known low-contrast token pairs.
- Visual QA fixtures cover at least one dense review gallery, one card grid, one table/callout layout, and one dark-theme artifact.
- Design Taste Gate review explicitly checks whether the visual system feels intentional rather than merely valid.

## Boundary

This note does not approve any SVG sample, theme, or new renderer behavior. It is a planning note for general Shareables design-system hardening.
