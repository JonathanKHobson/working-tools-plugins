# Release management

The public distribution has independently versioned plugins. The version authority is `catalog/packages.json`; its value is synchronized into all three supported plugin manifests. `catalog/source-inventory.json` fixes the reviewed distribution paths and exclusions. Historical source packages and downloads are not replaced. Separate guide/legacy downloads are registered in `catalog/external-products.json` with observed version schemes and provenance; a page-only guide is not an installation package. There is no distributed whole-ecosystem bundle to version.

## Completion event

Local queueing uses the Python standard library and configured source roots. Local Git supplies optional external/Site observations. Publication setup: create an isolated Python environment with `python3 -m venv .venv`, then `.venv/bin/python -m pip install -r requirements-release.txt`. Git, the authenticated GitHub CLI, and the existing Codex Sites connection are also required. The catalog runs both the checked-in JSON Schema and its semantic selection checks.

Routine local updates accumulate in a private queue. After editing the owning source, run:

```sh
.venv/bin/python scripts/complete_update.py --config "$RELEASE_CONFIG"
```

The default command refreshes `dist/release-manager/pending.json` and prints a local summary. For routine maintenance, repeat `--package <id>` for only the plugins just changed; this avoids rescanning unchanged owners and preserves other pending entries. Omit selectors when you want a complete local inventory refresh. `--status` is an alias for refresh plus status; add `--json` for the exact journal. It compares reviewed canonical/public bytes, reports unknown paths and conflicts for review, includes explicitly reviewed additions and records the registry's version as `recorded_version`, without claiming it is published. Missing semantic notes produce `pending-review`, not a version change or failure. It does not copy source, consume notes, change versions, build archives, contact a network, start Codex or overwrite the publication receipt. Full scans include registered integration hashes, configured active external-owner paths using local Git, and local Site changes compared with the saved `maintained_source_commit`, including working-tree changes, with explicit coverage boundaries. Scoped scans preserve all unselected existing journal entries.

The queue also reports the saved completion receipt as a read-only publication/recovery boundary, so prepared sources with matching inventory do not hide unfinished releases or Site promotion. It does not verify that receipt against live services.

The ignored journal is atomically written with mode `0600`, preserves `first_seen` for each pending product and has a stable fingerprint on unchanged reruns. Queue and release operations share the existing completion lock. A corrupt prior journal fails without replacement. No timer, count threshold, hook, daemon or scheduler promotes a queued item.

When the useful release batch is ready, explicitly run:

```sh
.venv/bin/python scripts/complete_update.py --config "$RELEASE_CONFIG" --publish
```

An urgent plugin release can use `--publish --package <id>`; repeat `--package` for the intended batch. `--prepare-only` is an explicit local preparation operation and cannot combine with `--publish` or `--status`. Recovery requires `--publish --reconcile-only`; `--reconcile-only` alone is rejected. `--publish` cannot combine with `--status`. Publication still runs the complete existing validation, exact-source release and Site deployment pipeline. The Site host uses the authenticated Codex deployment adapter; routine local queueing needs no AI session. The pending journal is reconciled only after successful completion. Failures preserve queued observations and leave recovery evidence in the separate publication receipt.

This explicit `--publish` operation, not a file save, interim commit, schedule or generic stop hook, starts publication. Codex maintenance routes routine work to the local queue and authorized release batches to `--publish`. Changes made outside Codex use this same command after their public update is complete. The authoring agent prepares a specific `catalog/changes/<product-id>.json` record from the diff with `level`, `summary`, `why`, `notes`, `compatibility`, `upgrade_guidance` and `validation`; the human does not separately compose notes, upload assets or edit links. An absent record stops before changing versions so unsupported semantic claims cannot become public release notes.

For a bounded plugin release, repeat `--package <registered-product-id>` for each intended plugin, including when using `--prepare-only` or `--reconcile-only`. This scopes source reconciliation, conflicts, pending records and recovery to those plugins and skips external-guide and integration publication. The Site catalog still reflects the full published release set. An unfinished receipt must be resumed with its original package scope; incompatible runs stop without replacing it. Omit `--package` for a full queue refresh or explicitly authorized full publication batch.

The private maintainer config contains `canonical_root`, `public_source`, `site_source`, `site_receipt`, `site_adapter` (an argv array), and optional `codex_command`. `external_checkouts` maps the active `shareables` and `what-is-an-mcp` owners to their public source checkouts. If a reviewed canonical product root is a symlink, `canonical_sources` must map its product ID to the exact absolute, resolved target directory, for example `{"product-id": "/absolute/reviewed/source"}`. A missing or changed target stops completion; symlinks inside a product remain disallowed. The maintained adapter is `["python3", "scripts/release_site_bridge.py"]`. It uses the authenticated Codex CLI Sites connector and requires that existing connection. Credentials are refreshed through the connector, not stored in this configuration. Recipient publishers configure their own source roots and hosting; no author paths are shipped.

With `--publish`, the command reconciles changes to already reviewed public paths, checks conflicts and exclusions, synchronizes manifests, creates a durable version record and package changelog, commits the intended files, validates the exact release commit, then pushes. Source-inventory validation always checks every public package and the complete reviewed baseline. During an independent release, live canonical included and excluded bytes are checked for the named releasing products; unrelated private work does not block them. A no-change completion checks the full public snapshot without claiming that other private source trees were audited. Standalone `scripts/source_inventory.py --canonical-root ...` still audits every canonical product and the canonical namespace. It builds deterministic ZIPs from the exact release commit and verifies their inventory. Publication uses draft, complete assets, downloaded-byte verification, then publish. A collision preserves the original release and stops with the exact discrepancy. There is no moving `latest/download` URL in the catalog.

Publication is strictly one-way: canonical source bytes are copied into the public plugin tree, and canonical is never written during `--publish` or `--prepare-only`. A canonical edit is detected and copied forward; a public-only edit (including a version bump, refreshed metadata hash, or a deliberately reviewed projection difference) is simply left as-is and is not written back into canonical. Only a path where canonical *and* public have both diverged from the recorded baseline into disagreeing content is a conflict, and that requires an explicit, separate authoring reconciliation outside publication — never an automatic reverse sync. `catalog/source-inventory.json` rows track this with two hash maps: `files` records the shipped public bytes (always checked against the public tree); the optional `canonical_files` records the last-known canonical bytes for the same paths once a release has run, letting the two sides diverge (e.g. after a version bump) without the next `plan()` mistaking that divergence for a fresh canonical edit. Importing a public-only edit back into canonical, when actually wanted, is a separate explicit authoring action taken outside this release tooling — publication itself never performs it.

A new public file or removed source must receive an explicit review in the existing source inventory/provenance/coverage records. That review can be completed by the authorized authoring agent. After adopting exact canonical/public bytes and their current hash in the inventory, list added package-relative paths in the change note as `"reviewed_additions": ["references/new-method.md"]`. Each listed path must already have matching provenance output hashes and license coverage; the command never creates these review entries. This explicit list triggers a release even when the newly reviewed inventory hash already matches both copies. The consumed note prevents an unchanged rerun from repeating the release. License and public-file metadata refresh current hashes and versions in dependency order using their existing row scope and exclusions. Historical source/upstream hashes and license grants remain intact. Generated license-scope and public-file changes are included in the scoped commit and durable changed-file record. The command never imports unreviewed private files or runs historical one-off exporters. For public contributions, reconcile the reviewed public edition with the local authoring source before export, preserving conflicts for resolution.

## Incorporated methods and package completeness

Reusable skills and ordinary helper scripts ship within their maintained Studio or Toolkit. Do not turn an incorporated method into a separate-install prerequisite during public packaging. An external API, app connection or required runtime has an execution boundary; a method-only marketplace bundle does not. The package validator rejects the retired overlapping method packs in installation requirements, while preserving genuine apps, runtimes and official OpenAI providers. Retained third-party material keeps its required notices; newly authored methods use the package's first-party license.

Before any batch mutation, every affected package needs a reviewed local changelog and complete semantic notes. Historical changelogs may be initialized from verified release records with their provenance stated; never rewrite published package bytes. Release metadata preserves either supported file-manifest shape. Products built from the same exact source commit share one build within a publication call, while asset, version and publication checks remain per product.

## Versions and compatibility

Compatible corrections, including instruction/reference changes, normally increment patch. Compatible optional capabilities increment minor. Removing invocation IDs, required installation/configuration contracts or supported inputs/outputs needs a major change. Review behavioral instruction changes explicitly; a file extension alone cannot determine compatibility. Build metadata retains historical identity but does not control SemVer ordering. Independent plugins keep independent versions; the highest eligible stable version is selected per product, not by repository-wide Latest or publication date. Prereleases, drafts, withdrawn records and unavailable packages do not automatically advance current downloads. A maintenance backport remains in history without replacing a higher stable line.

Every reviewed shipped file contributes to change detection. The local queue reports hashes and relative paths without logging file contents or private configuration. Excluded source is outside release scope. Unknown files remain review signals and are never imported; resolving those signals does not imply release permission. External queue checks compare only registered owner paths to the recorded local Git revision. Site queue checks use the saved Site receipt's `maintained_source_commit` as a deployment baseline when available, plus local working-tree and untracked changes. Missing or unreadable receipts explicitly report an unknown deployment baseline; the queue cannot then confirm committed unpublished Site changes. Local Git disables lazy object fetching. No queue check verifies live deployments or remote availability. The private `shared_shipped_paths` map assigns a repository-relative shared source to its already-reviewed installation destinations, for example `{"shared/template.md": ["plugins/a/references/template.md", "plugins/b/references/template.md"]}`. The queue observes shared input changes before destination copies. The explicit publication operation reconciles those bytes and releases every affected product; a conflict with separate edits stops before publication. Website-only edits, version records outside packages and unchanged reruns do not cause package versions. A release containing changed shipped changelog or instructions requires a new package version; corrections to external notes/catalog metadata can reconcile without changing package bytes.

## History and deployment

`python3 scripts/sync_release_catalog.py` imports every GitHub API page, resolves each tag, checks installation archives against the exact tagged source tree, and validates `catalog/release-history.json`. Verified evidence can be reused only when commit and GitHub asset name, URL, size and digest still agree. Failed history lookup cannot truncate the prior catalog. Separate external records retain original links, observed checksums and reconstruction limits.

The Site adapter uses the private configuration's explicit Site contract. `static-dist-v1` updates the current managed Sites checkout and its existing redesigned `dist`, using the owning workspace's guide and skill-link generators. It never rebuilds that Site from a legacy source tree. The receiving request freezes protected-file and guide-header hashes; stamping and the final promotion check reject changes outside the catalog boundary. New skill guides need factual authored coverage; absent coverage produces `catalog_pending`, not invented copy.

Routine updates to an existing skill refresh its generated download block from the current verified skill catalog without rebuilding or editing its authored guide. The guide keeps its explicitly stated review version/source even when a newer bundle is available. Strict guide generation is optional and applies only to supplied editorial sources already reconciled and reviewed for that release. A version difference alone does not block download maintenance; new/removed skill identities or missing routes still require an exact coverage report rather than invented guide copy.

The static contract projects exact release-history and skill-download catalog bytes, stages reviewed changes, then invokes `release_site_bridge.py --stamp-static-site <site> --site-request <request>` before the source commit. Its `release_projection` binds the complete staged static payload (excluding the manifest itself), project identity and catalog hashes. Historical `source_revisions` remain upstream lineage, not the current Sites source commit. After authenticated fast-forward source push and native Sites deployment, the receipt must bind the clean local, remote and saved-version source commits and unchanged audience/access revision. Both catalogs and the projection stamp are read back from production. Prior receipts always receive a native source check: a verified unchanged version is reused with `no_op=true`, without another build, push or deployment. Old pinned-source mode remains available for an explicitly configured legacy Site.

The release labels and URLs come from the same catalog record. Product IDs, version records and `/plugins/<id>/releases/<version>/` addresses survive display-name or visual rebranding. No private workstation bindings enter public source.

Local completion and Site promotion have separate locks. The Site adapter rechecks canonical release state immediately before promotion and refuses stale input. Source pushes are fast-forward only. A newer published package cannot be overwritten by an older catalog job. Publication does not rely on a `release` event launching another workflow with `GITHUB_TOKEN`.

## Recovery

```sh
.venv/bin/python scripts/complete_update.py --config "$RELEASE_CONFIG" --publish --reconcile-only
```

Recovery resumes a draft or verifies identical published assets, then retries catalog synchronization without allocating another version. If GitHub succeeds and the Site fails, retain both the published packages and the prior live Site. The receipt stays `catalog_pending` until exact live catalog readback. `dist/release-manager/receipt.json` and the configured Site receipt distinguish preparation, publication and deployment; ignored build/cache files contain no canonical version authority.

Focused fixtures cover default offline isolation, stable queue fingerprints, scoped preservation, corrupt journal retention, review signals, failed publication, registered external/integration/Site boundaries, instruction/template detection, website/no-op isolation, semantic ordering, pagination failure, exact-byte collisions, incomplete drafts and recovery. They do not create artificial public test releases. Runtime installation, visual keyboard/mobile checks and publication readback remain separately recorded acceptance evidence.

Independent active guides use the integrated external completion step and [owning-repository recovery](external-release-management.md). Frozen legacy resources remain unchanged.

The independently installed optional host-hooks integration has its own version authority in `catalog/integrations.json`, outside the plugin marketplace. See [integration pack releases](integration-release-management.md).
